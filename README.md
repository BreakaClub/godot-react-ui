# godot-react-ui

A standalone prototype of React TSX in GodotJS, with Rust/Taffy layout and native Godot drawing. It is not integrated into `breaka-rpg`.

One repository contains the GDExtension, the `godot-react-ui` TypeScript package, and an interactive Godot demo. Keeping them together lets the native protocol and renderer evolve together while the boundary is experimental. The package is marked `private: true`; it has not been published. Repository creation and local builds do not create a remote, push, or deploy anything.

## Run the native demo

The current native addon manifest targets Apple Silicon macOS. Use Breaka's Godot 4.8 V8/GodotJS build (the default engine) or stock Godot 4.7.2 with upstream GodotJS (`--engine=stock`; both load the same native build, see "Engine profiles and installed builds"), Node.js, pnpm 11.5.2, and rustup. `rust-toolchain.toml` pins Rust 1.99.1. The build uses rustup's Cargo, avoiding this workstation's unrelated Homebrew Rust installation. The demo is also hosted at [react.breaka.club](https://react.breaka.club), the Web export served by a Cloudflare Worker (see "Verification and Web").

```sh
export GODOT=/Applications/Godot48.app/Contents/MacOS/Godot
pnpm install
pnpm build:native
pnpm build
pnpm demo
```

`build:native` compiles the optimized Rust library and installs it into `demo/addons/godot-react-ui/bin/`. `build` typechecks before bundling the demo and emitting CommonJS, ES modules and declarations into `dist/`. The demo's bundles contain React and `react-reconciler` built for production (`process.env.NODE_ENV` is `"production"` in `scripts/build.mjs`); `dist/` leaves both as imports. Both package entry points are importable; `pnpm pack` creates a local npm tarball without publishing. Generated GodotJS declarations and scene wrappers are included under `demo/typings/` and `demo/gen/`; `.uid` files are project metadata. Compiled libraries, JavaScript bundles, and the `.godot` import cache are generated locally.

`pnpm demo` opens a **lab navigator**: a sidebar of every lab by group (a top bar with the kit's `Select` below 1024 logical pixels), a filter, a header with the lab's title and description and Previous and Next (also Alt+Up and Alt+Down), and the lab in a clipped, scrolling content area with an error boundary of its own. A lab that needs the whole window (frosted glass) or is its own scene (world space) shows a card and a button for it, with a way back that stays on screen. `--lab=<id>` (`pnpm demo --lab=glass`; `?lab=<id>` on the Web) opens a lab, and an unknown id is an error on screen. The labs are one array, `demo/src/labs.tsx`: adding a lab is one entry (id, title, description, group, how it is shown, its TSX sources). `pnpm demo:web` serves the Web export and prints the address.

**Code editor.** The **Code** button of a lab (not offered below 768 logical pixels, nor for a window or scene lab) reveals that lab's TSX in an editor made of the library's own components: type, and the page above updates after a short pause, with its state kept where the hooks are the same. A syntax or type error leaves the last good page on the stage; type errors, hover types and inlay hints come from Bun's TypeScript checker and compiler, drawn as wavy underlines, inlays, a problems list and a status line. The text lives in CodeMirror 6's headless `EditorState` (Lezer highlighting, history, several selections, CodeMirror's key table); the view is a window of lines, each one `Text` with nested `Text` spans ("Rich text" below) and a caret and gutter; a focused `TextInput` at the caret takes the keyboard, the IME and the soft keyboard and is never edited. The checker and compiler are a separate, demo-only GDExtension, `live-compile/` (its own cargo workspace and Rust nightly; nothing in the package gains a dependency or bytes), built by `node scripts/build-live-compile.mjs` (`--cli` also builds a native test process; `node scripts/build-live-compile-web.mjs` builds the Web side module). Without it the code is shown read-only, with the reason. See `demo/src/editor/`, `demo/src/live-compile-*.ts`, [docs/tracks/code-editor.md](docs/tracks/code-editor.md) and [docs/tracks/live-compile.md](docs/tracks/live-compile.md).

What a run opens with: `--lab` or `--demo=navigator` opens the navigator, `--demo=app` the single-page playground; with neither, a run that injects its own input (a verifier) opens the playground and every other run the navigator. The Web page's bare address opens the playground (that is what the Web verifiers load), and `pnpm demo:web` and the Worker send it to `?demo=navigator`. The playground has four tabs:

- **Counter:** real React state, derived values, closures, effects, context, disabled buttons, pointer states, and keyboard activation.
- **Inventory:** a responsive Taffy grid, keyed component state, reordering, filtering, insertion/removal, and an empty state.
- **Interaction:** the event pipeline: capture and bubble with `stopPropagation()`, `preventDefault()` that stops native's focus default action, synchronous dispatch (a handler observes native state before its default action runs), `pointerenter`/`pointerleave` that reach only the elements crossed, and handlers that remove their own target, detach the root from the scene tree, or unmount it while native is still inside the press.
- **Motion:** native Blitz/Stylo CSS transitions (`width`, `height`, `opacity`, `backgroundColor`), intrinsic `0 ↔ auto` height transitions (`interpolateSize: 'allow-keywords'`), rectangular clipping (`overflow: 'hidden'`, `'scroll'`, `'auto'`) for both rendering and hit testing, in-flight retargeting across text/font/width/viewport changes, rapid reversal, tree detach/reattach pause/resume, and active-transition removal.

Resize the window to see `md:` classes recompose the layout. Tab and Shift-Tab move between enabled buttons; Enter and Space activate them. All provided Godot launch scripts use `--audio-driver Dummy`.

The demo owner also puts a full-window Godot `ColorRect` behind the React root and counts what reaches it and `_unhandled_input`. The verifiers render pages through `godotReactDemo.showLab(name)`: a HUD over it (`'hud'`: every ancestor is `pointer-events-none`, a few controls are `pointer-events-auto`) to prove that empty space, keys the UI did not use, and wheel ticks it did not consume belong to the game.

### Engine profiles and installed builds

Every build, run and verify script takes the same engine selector, and `breaka` (Breaka's custom Godot 4.8 with its GodotJS) is the default:

```sh
pnpm verify                          # breaka: /Applications/Godot48.app, evidence under artifacts/
pnpm verify --engine=stock           # stock Godot 4.7.2 + upstream GodotJS, evidence under artifacts/stock/
GODOT_REACT_ENGINE=stock pnpm verify
```

`--engine=<name>` wins over `GODOT_REACT_ENGINE`; an unknown name is an error. `stock` defaults `GODOT` to `/Users/ben/Development/godot-stock/bin/godot-stock` (a wrapper that redirects `HOME`, so a run cannot write to the user's Godot folders; see that tree's `BUILD_NOTES.md`). `GODOT` still overrides either profile's binary; its `--version` must match the profile and be at least 4.7.2.

**The native builds are one build, whichever engine runs them.** The UI library (`pnpm build:native`) and the live-compile extension (`node scripts/build-live-compile.mjs`) are bound to the Godot 4.7.2 API (`NATIVE_BINDING_API` in `scripts/native-binding.mjs`; the dumps are `native/api/stock-4.7.2`), which Breaka's 4.8 loads as well as stock 4.7.2 does: a GDExtension loads in the Godot it was bound to or a newer one, never an older. Each installs over the one path its `.gdextension` names and records the API and the dump hash it was bound to, not a profile; `--engine=` does not apply to them and is refused. Switching between `--engine=stock` and the default needs no build and no install. Breaka's 4.8 resolves each Godot method the library calls on first use (godot-rust's lazy function tables), so a method missing from its class table would fail at its first call; which sections ran on both engines with the one build is recorded in [docs/tracks/single-build.md](docs/tracks/single-build.md).

**What stays per engine profile** is the Web (`pnpm build:web --engine=<name>`, and `node scripts/build-live-compile-web.mjs`, which builds the `breaka` profile only): a Web side module is linked with the Emscripten of the engine whose templates load it, 6.0.12 with Breaka's lazy function-table ABI for `breaka` and 4.0.11 for `stock`, and Breaka's Web side module is still bound to Breaka's own 4.8 dumps (`native/api`); the GodotJS typings (`demo/typings` and `demo/gen` are Breaka's; the stock ones are generated by the stock editor from the one native library into `target/stock-typings`); and the evidence directories (`artifacts/` and `artifacts/stock/`). On Web the `stock` profile uses the stock templates (debug and `--release`; [docs/WEB.md](docs/WEB.md) has the commands).

**After a checkout or a merge, build once:** `pnpm build:native`; `node scripts/build-live-compile.mjs` where the code editor's extension is installed; `pnpm build:web` for each profile in use, and `node scripts/build-live-compile-web.mjs` where the Web code editor is used (`.cargo/config.toml` is an input of every build's digest, so a change to it makes every Web side module stale). A run that needs one of them says so, with the command, before any window opens. The stock typings regenerate by themselves on the next `pnpm test:types --engine=stock`.

**Installed builds are checked against the source.** A build records what it was made from: a SHA-256 of the contents (never the modification times) of `native/` (without its API dumps and Markdown), `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/config.toml` and `build.rs` if present, and the API dump pair it is bound to, plus the cargo features it was built with. It is written into the stamp beside each installed build (`react_ui.build.json`, `react_ui.web.build.json`; a native stamp records the Godot API and the dump's hash it was bound to, a Web stamp the engine profile, and both the probe flag and the library hash), beside cargo's own output in the target directory, and into a Web export's `build-receipt.json` (`extension`). Every script that runs or serves a build compares that with the working tree first and refuses, naming the files that differ and the command that rebuilds: the native verifiers, `pnpm demo`, `pnpm dev` (at startup), `pnpm gen:types`, the Web verifiers and `pnpm demo:web`, the Web export, and `pnpm test:types --engine=stock`, which checks the native library its typings are generated from and never builds it. An installed live-compile extension is checked the same way on every native run (a demo run loads it whether or not its section runs); an absent one is fine, the code editor is then read-only, and only the `live-compile` section is refused. A library or extension bound to another API (a stamp that names an engine profile is a build from before the single build and is one), an engine older than 4.7.2, and a probe build for a default run (nor a `--faults` build, a feature set of its own) are refused too. The refusal comes before any window or browser opens. A Web export's receipt also records a digest of the TypeScript, demo and script sources it was bundled from, the engine template, and each exported file's size and hash; the guard checks all of it, and the fix it names for those problems is `pnpm build:web --export-only`. What the guard does not cover: the Rust and Emscripten toolchains beyond `rust-toolchain.toml`, the engine itself, the compiled JavaScript, and the tracked `demo/typings`; a hand-run `cargo build` changes the library under a stamp that does not describe it (the next `build:native` cleans and rebuilds); and godot-rust's generated bindings follow cargo's own tracking of the API dump's mtime, so a dump restored with an old mtime would not rebuild them (do not edit a dump by hand).

`build:native` and `build:web` do not rely on cargo's own check, which compares modification times and so keeps an artifact when a source is restored to older content with its old mtime. Unless the target directory's stamp says its artifact is a build of exactly the current sources, they run `cargo clean -p godot-react-ui` first (this crate only; the dependencies stay cached), and `build-live-compile.mjs` does the same for its two crates. The first build after the guard was added therefore recompiles the crate once. Decisions and limits: [docs/tracks/freshness.md](docs/tracks/freshness.md), [docs/tracks/stock-engine.md](docs/tracks/stock-engine.md) (the stock profile; its per-profile native builds, S2 to S4, are superseded) and [docs/tracks/single-build.md](docs/tracks/single-build.md). [docs/tracks/engine-switch.md](docs/tracks/engine-switch.md) records a switch between per-profile native builds that the single build removed.

For TypeScript iteration, run `pnpm dev`. It watches the demo bundle and opens the Godot editor; run the demo there and restart its scene when changing initialization. Native extension changes require rebuilding and restarting Godot because extension hot reload is disabled. `pnpm dev` refuses to start on a library that is not a build of the current sources; it does not check again while it runs.

### What a PASSED line means

Each native verify script prints a summary after its windows. Read it, not just the exit code (docs/tracks/verifier-integrity.md):

- `landscape: PASSED` is a run that passed on its first launch. `PASSED (PARTIAL: not run: pointers, drag, …)` is a run that left sections out (`--only=…`; a plain `verify:interaction` runs every default section and is not partial), or checks out (`verify:text-layout --headless` runs no pixel checks; the platform focus check of `verify:a11y` is skipped when the window is not the key window). A partial run is not the verification. `(N recorded engine gap(s), not failures: …)` lists what an engine cannot convey that a verifier recorded instead of failing; `(a disturbance reached its window, but it passed)` says something reached the window and the run passed anyway.
- `PASSED after N disturbed failure(s). First failure: …` is a run that failed, was disturbed by something that reached the window (a real mouse event, a focus loss with a press in flight) shortly before it failed, and passed on a re-run. Its first log and captures are kept (`run-attempt-1.log`, `<window>-failed-attempt-1/`). A failure with no such disturbance is real and is not re-run. `--no-retry` runs each window once: use it for negative controls, where a re-run would hide the failure you are looking for.
- Every window is also refused if the installed library stopped matching the sources since the script started.

A verifier run keeps its own clipboard and never touches the Mac's: native runs hold it in the process's memory (`ReactUiRoot.isolateClipboard(true)`), and `verify:interaction:web` replaces `navigator.clipboard` with an object in the page's memory (no permission is requested). Whether headless Chrome would have reached the system pasteboard, and the engine's own last step onto the Mac's pasteboard, were not measured, because measuring writes to it.

On macOS the native verifier windows never take focus. The engine cannot be asked not to (`show_window` always activates the application), so `scripts/native-run.mjs` loads `scripts/quiet-window/quiet_window.m` through `DYLD_INSERT_LIBRARIES` into automated runs only: the application's activation policy is forced to accessory (no Dock icon), the activation calls do nothing, the window cannot become key or main, it is transparent and click-through, joins every Space and always reports itself visible (the engine stops drawing a window it thinks is covered), and a scene still draws and reads its pixels back (checked on Breaka's engine with the Compatibility, Mobile and Forward+ renderers and on stock 4.7.2 with Compatibility). It fails closed: a verifier run whose log lacks `QUIET_WINDOW_LOADED`, or that logs `QUIET_WINDOW_ACTIVATED` or `QUIET_WINDOW_MISSING`, fails. `node scripts/quiet-window.mjs <godot> [arguments]` does the same for any other Godot command, and `pnpm demo` and `pnpm dev` do not load it, so a person's own window behaves as normal. Other platforms start the command unchanged (`docs/tracks/quiet-windows.md`).

## Editing TypeScript: use an external editor

Godot's script editor does not understand TypeScript. If a `.ts` or `.tsx` file is open in it when the editor saves, it rewrites the file (tabs for the indentation it thinks is wrong: `demo/src/main.ts` came out with 254 changed lines). The scripts that launch an editor (`gen:types`, the import step of `pnpm demo` and every native verifier, the stock typings, `pnpm dev`) take TypeScript out of the project's saved editor layout first (`build:web`'s headless export included), so none is opened by them. That cannot stop you opening a `.ts` file by hand in the Godot editor: edit TypeScript in an external editor, and keep it closed in Godot's.

## Authoring

Use ordinary React, including hooks and component composition, with five native primitives (`View`, `Text`, `Button`, `Portal` and `TextInput`) and a small component kit built from them (`Checkbox`, `Switch`, `RadioGroup`, `Slider`, `Select`, `Combobox`, `TextField`, `ScrollView`):

```tsx
import { useState } from 'react';
import { Button, StyleSheet, Text, View } from 'godot-react-ui';

const styles = StyleSheet.create({
  panel: { padding: 24, borderRadius: 16, backgroundColor: '#ffffff' },
});

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <View style={styles.panel} className="gap-4">
      <Text className="text-3xl text-slate-900">Count: {count}</Text>
      <View className="flex-col md:flex-row gap-3">
        <Button
          className="rounded-lg bg-indigo-600 hover:bg-indigo-700 active:bg-indigo-800 text-white px-4 py-3"
          onClick={() => setCount(value => value + 1)}
        >
          Add one
        </Button>
        <Button
          disabled={count === 0}
          className="rounded-lg bg-slate-100 text-slate-700 disabled:text-slate-400 px-4 py-3"
          onClick={() => setCount(0)}
        >
          Reset
        </Button>
      </View>
    </View>
  );
}
```

`View` defaults to a flex column. `Text` uses Godot text shaping and wrapping; as in React Native, raw strings may only appear inside `<Text>` (a raw string in a `View` throws); a `Text` inside a `Text` is a span of one attributed paragraph ("Rich text" below). `Button` participates in native hit testing and keyboard focus and renders its string and number children as one `Text` label. `Portal` renders its children into the overlay layer, which always draws above the main layer and is hit-tested first. Each `<Portal>` has its own container in that layer (React's persistent mode replaces a portal container's whole child list whenever that portal changes and empties it when the portal is deleted, so portals that shared one erased each other), so any number can be open at once; the overlay's top level is their children together, oldest portal first, so what opened last paints on top. `color`, `fontSize`, `textAlign`, `pointerEvents`, `cursor`, `userSelect` and `selectionColor` inherit natively. Focus: `Button`s, and any element with `tabIndex={0}` (in the tab order) or `{-1}` (focusable only), take focus from a press, Tab (document order, wrapping, never a disabled or invisible element), `handle.focus()` or `autoFocus`. The focus ring and `focus-visible:` styles mark a keyboard focus only (Tab, or `focus()` after keyboard input); a press focuses without them. `onKeyDown`/`onKeyUp` (cancelable `keydown`) carry DOM `key`, `code`, `repeat` and the modifiers; Enter and Space press a focused `Button` and click it on release, without pointer events (a prevented `keyup` ends the press with no click), and a focus trap is a few lines of `onKeyDown`, `preventDefault()` and `focus()`. Events include `onClick`, `onDoubleClick`, `onAuxClick` (any button but the primary), `onContextMenu`, pointer enter/leave/down/up/move/cancel (each with a `Capture` variant except enter/leave and the click family beyond `onClick`), `onWheel` (cancelable; deltas are in wheel ticks, positive down and right) and focus/blur. A `click` goes to the nearest common ancestor of the press and release targets, as in browsers (two parts of one enabled button click the button; a release on a disabled element or over nothing clicks nothing). They have DOM semantics: capture handlers run outermost first, then bubble handlers from the target up, then root listeners (`root.addEventListener`); `pointerenter`/`pointerleave` do not bubble and run only for the elements the pointer crosses. Events provide `target`, `currentTarget`, `eventPhase`, root-local coordinates, `pointerId`, `pointerType`, `button`, `buttons`, modifiers, `timeStamp`, `stopPropagation()` and `preventDefault()`. A pointer press is dispatched synchronously from inside Godot's input callback, so `preventDefault()` on `onPointerDown` stops native's focus default action before it runs. Pointers: the mouse (pointer 1, every button, click counting in `detail`) and touches (pointer 2 and up, multi-touch, captured to where they went down; the engine's mouse emulation is ignored, so a touch is never also a mouse press and never hovers) produce DOM pointer events. `handle.setPointerCapture(pointerId)` (also `releasePointerCapture`, `hasPointerCapture`) routes a pressed pointer's moves, up and cancel to an element wherever it goes, including outside the root and the window; `pointercancel` ends a contact the OS, a lost window focus or a detached root interrupted. Godot co-operation: the root takes pointers only where an element can receive them, so empty space and `pointer-events: none` regions (when every ancestor is `none` too) reach the Godot `Control`s underneath and then `_unhandled_input`; `cursor-*` sets the window cursor through the root's `_get_cursor_shape`. The root takes no key focus when it enters the tree: its owner calls `grabFocus()` for keyboard-first behaviour, and an element taking focus grabs it. Tab is consumed only when it moved focus, Enter and Space only when they activated a focused button, and a wheel tick only when a handler calls `preventDefault()`; everything else reaches `_unhandled_input`. A press on something that cannot take focus hands key focus back to the game. `viewportX`/`viewportY` are canvas coordinates (what `_unhandled_input` receives), `x`/`y` are root-local. Positioning follows CSS with React Native's `zIndex`: `position` (`static`, `relative`, `absolute`, `fixed`; no `sticky`), `top`/`right`/`bottom`/`left` (pixels, percentages, `auto`; negative allowed; the `inset` shorthand and the `top-4`, `inset-0`, `inset-x-0`, `left-1/2`, `-top-2` utilities) and `zIndex` (the `z-10`, `z-[3]`, `-z-10` utilities). An `absolute` element is placed in, painted by and clipped by its nearest positioned ancestor (else the root), not by its parent: a menu in an `overflow-hidden` card stays visible where its containing block is outside the card. `zIndex` orders the elements one parent paints; there are no stacking contexts. `<Portal>` content is positioned like any other (`absolute inset-0` is a full-window backdrop); read an anchor's rectangle with `getRect()`. Events from inside a portal bubble through the overlay tree, not through the React ancestors of the `<Portal>`, and its Tab stops come after the main layer's. Scrolling: `overflow` `scroll` or `auto` on an axis makes a scroll container (the kit `ScrollView` wraps one with a content element that cannot shrink). The wheel, a trackpad pan, the keyboard (arrows, Page, Home, End, Space on the focused element's container; Tab and `focus()` scroll their element into view), a touch pan with momentum and an overlay scrollbar thumb dragged with the mouse all scroll it; a scroll the innermost container cannot take chains to the next one unless it has `overscroll-contain`, and a wheel tick nothing can take reaches `_unhandled_input`. `onScroll` (coalesced, not bubbling) and the handle's `scrollTo`, `scrollBy`, `scrollIntoView` and `getScrollState` read and move it. A touch that moves beyond 8 px pans the container unless `touch-action` forbids it, which cancels the pointer and its `click`; `touch-none` keeps the pointer events (the kit `Slider` has it). Scrolling moves one canvas item: no commit, layout, restyle or re-record happens (the snapshot's `scrollUpdates` and `overlayRecords` are what change). Text selection: `select-text` (inherited; the default is `select-none`) lets the mouse select the text of `Text` elements: a click collapses, a double click selects a word, a triple click the node's text, dragging extends (across elements, skipping `select-none` text, and to the start or end of the text after or before a pointer that is not over text) and Shift+click extends. A press on a `Button`, on an element that captured the pointer or prevented `pointerdown`, or on anything not selectable starts nothing and clears the selection. A selection takes Godot key focus for the root (no element is focused) so `ui_copy` (Cmd/Ctrl+C) puts the selected nodes' text, joined by newlines, on the clipboard and `ui_text_select_all` selects all selectable text; changing or removing text the selection covers clears it. `selection-[#hex]` colours the highlight, which is drawn under the text in the content item, so it scrolls and clips with its container; selectable text shows the text cursor. `root.addEventListener('selectionchange', ...)` (no payload, coalesced), `root.getSelection()` (the anchor and focus as element handles with UTF-16 offsets, the selected `text`, `isCollapsed`), `root.clearSelection()` and the `useTextSelection()` hook read it. Drag and drop follows HTML inside one root: `draggable` (and `dragPreview`: `native`, a translucent copy of the element that follows the pointer, or `none`) makes an element a drag source, once a mouse moves past `Viewport`'s drag threshold or a touch is held still for half a second (a touch that moves first pans instead, and a prevented or captured `pointerdown` starts nothing; text inside a draggable element starts no selection). `onDragStart` (cancelable; fills `event.dataTransfer`), `onDrag`, `onDragEnter`, `onDragLeave`, `onDragOver` (cancelable: preventing it makes the element a drop target for the `dropEffect` the handler leaves, if the source's `effectAllowed` permits it), `onDrop` (cancelable) and `onDragEnd` (`dropEffect`, root-local and viewport coordinates, and `endedOutsideRoot` for a release beyond the root) all bubble; starting a drag cancels the pointer (`pointercancel`, no `click`). `DataTransfer` has the HTML protection modes (`setData` in `dragstart` only, `getData` in `drop` only). The cursor shows can-drop or forbidden, Escape cancels, a scroll container scrolls when the pointer rests near its edge, and the target follows a scroll under a stationary pointer. Hover, press and focus are native state: they restyle `hover:`, `active:`, `focus:`, `focus-visible:`, `focus-within:` and `disabled:` variants without any React render or JS call. Refs expose a typed handle with its native tag and `getRect()` (a native query); `testID` supports inspection and `findByTestID` (a native query) without becoming native identity.

### TextInput

`TextInput` (and the kit's `TextField`) keeps its text natively and follows React Native's controlled-input protocol: pass `value` and store what `onChange` reports, or pass `defaultValue` and leave it alone. An edit is applied first and reported (`beforeinput`, then `input`); a `value` that differs from the text the user made is sent back with `setTextAndSelection`, so an `onChange` that stores something else (capitals, a filtered string, the old value) takes effect at once. Two consequences that a developer used to a plain `<input>` can trip over, and that a controlled `<input>` in a browser has too:

- **The caret goes to the end when a controlled value changes the length of an edit.** It stays where it was when the value has the length of the edit's text (a transform such as capitals) or goes back to the text from before the edit (a rejected edit, with the selection it had). Any other value, a mask that adds separators for instance, puts the caret at the end of the new text.
- **`setTextAndSelection` clears the undo history.** A controlled field whose `onChange` rewrites what was typed, or refuses some of it, has no undo for the text before the rewrite.

Also: `multiline` is fixed when the input is created (a commit that changes it is rejected); a paste with no text pastes nothing; a triple click selects all of a text area's text, not a line (`LineEdit`'s rule); a `TextInput` is always a text field to assistive technology (its `role` can only remove it from the tree); and there is no `aria-labelledby` or `aria-describedby` (native rejects unknown props), so the kit's `TextField` sets `aria-label` and `aria-description`. The text utilities (weights, families, tracking, line height) are accepted on a `TextInput` and do nothing: it shapes with the theme font.

### Combobox

`Combobox.Root`, `Control`, `Input`, `Clear`, `Trigger`, `Content`, `Item`, `ItemText`, `ItemIndicator` and `Empty` make an editable combobox (the WAI-ARIA editable combobox with list autocomplete): a `TextInput` with `role="combobox"` that filters a list in the overlay layer while keyboard focus stays in the input and the active option is announced through `aria-activedescendant`. `multiple` makes it a multi-select whose choices are chips (`Chips`, `Chip`, `ChipRemove`; the chips and the input wrap together in the control, so `Chips` takes the `Input` as its child). Typing filters (`filter`: a function, or `null` for options a parent fetches) and opens; ArrowDown and ArrowUp open and move (they go round), Alt+ArrowDown and Alt+ArrowUp open and close, Enter chooses, Escape closes and then clears, Home and End are the caret's, and Tab leaves and chooses nothing; `allowCustomValue` makes typed text a value (Enter, or a comma in a multiple one). Backspace in an empty input moves onto the last chip and a second press removes it. There is no backdrop: a press outside reaches what is under it and the input's `blur` closes the list, and a wheel anywhere but over the list closes it too (`useRootEvent('wheel', ...)`, a document-level listener, is exported). A mouse press on the list is prevented to keep focus in the input; a touch is not, because a prevented press cannot become a pan, and the list gives the focus straight back to the input. `value`, `inputValue` and `open` are controllable, and `value` is typed by `multiple` (`string | null`, or `readonly string[]`). Options are children, as in `Select`; a thousand options cost what a thousand `Select` items cost (about 110 ms to open, measured in JavaScript against the recording host, not natively), and there is no virtualisation. Details and the 46 mutants of the unit tests: [docs/tracks/combobox.md](docs/tracks/combobox.md).

### Rich text

A `Text` with nested `Text` is one attributed paragraph, as in React Native: `<Text>const <Text className="text-purple-600">x</Text> = 1</Text>` is one native node with a styled range. A span sets colour, background colour, font family, weight and slant and the text decoration (`underline`, `overline`, `line-through`; `decoration-solid|double|dotted|dashed|wavy`, thickness, colour, `underline-offset`), inherits from the span it is in, and is drawn per glyph over one shaped paragraph, so monospace columns are exact. Decorations are drawn as Chrome draws them, wavy included. `<Text inlay>` is generated text (a type hint): shown, measured and wrapped, but not part of the text: offsets, the selection, copy and the accessible name skip it, and a caret can sit on either side of it. Every `Text` handle answers `getCaretRect(offset, side)`, `getOffsetAtPoint(x, y)` and `getRangeRects(start, end)` in the root-local space of `getRect()`, right under transforms and at any pixel ratio. A change to one span's colour is a commit of a few hundred characters that paints without shaping again. A nested `Text` accepts only `children`, `className`, `style` and `inlay` (no ref, handler, `role` or `testID`, because it is not an element), its style may set only the longhands above, and a font size, letter spacing, case or breakpoint or state class on one throws, naming it; a `View` or `Button` inside a `Text` throws. The nesting is flattened in the renderer's host config, as React Native does with virtual text nodes, so an app with no nested `Text` takes the old path. Details and the Chrome comparison: [docs/tracks/rich-text.md](docs/tracks/rich-text.md).

### Accessibility

`role` (the ARIA names of `UIRole`) and the `aria-*` props of `UIAriaProps` (`aria-label`, `-description`, `-valuetext`, `-placeholder`, `-hidden`, `-disabled`, `-expanded`, `-selected`, `-readonly`, `-required`, `-modal`, `-checked` including `'mixed'`, `-valuemin`, `-valuemax`, `-valuenow`, `-live`, `-orientation`, and `-activedescendant` and `-controls`, which name an element by the `id` of its handle because native has no DOM ids) reach Godot's `AccessibilityServer`. Native keeps one accessibility element per exposed node: a `Button`, a `Text` with text, a `TextInput`, a scroll container (`SCROLL_VIEW`) and anything with an explicit `role`; `aria-hidden` removes a subtree. Each has a name, role, state and bounds that follow scrolling, and actions: click, focus, a text input's selection and edits (through `beforeinput`), a slider's increment, decrement and set value (`onAccessibilityAction`; the kit `Slider` answers it), the scroll actions, and a scroll bar element for each scrollable axis. The kit sets its own roles and states. What was verified where (the macOS tree was read only on the `stock` engine profile, which has AccessKit; Breaka's engine has no accessibility driver; VoiceOver was never run by hand) is under "Current limits".

### Mounting

Mount with `createRoot(nativeSurface, { subscribeToEvents }).render(<App />)`, where `nativeSurface` is a `ReactUiRoot` from `godot`. `subscribeToEvents(listener)` is required: the owner connects a `Callable` for `listener` to the surface's `eventsReady` signal and returns a function that disconnects it (a GodotJS `Callable` holds its function strongly, so `unmount()` calls that function or the whole root would stay reachable). Native emits `eventsReady` from inside its input callbacks. The owner also sets the surface size (native restyles the nodes whose breakpoints the new width crosses, with no React render), calls `dispatchEvents()` each frame for events native queued outside an input callback, and calls `unmount()` before freeing the surface. [The demo owner](demo/src/main.ts) shows the complete lifecycle, including tree re-entry. `render()` commits the initial render synchronously; later hook updates use React's scheduler.

### Display scale

The root draws its text and its rounded edges at the font oversampling of the viewport it is in (`Viewport.get_oversampling()`), which is what Godot's own controls draw at. A `Window` carries its content scale factor, a stretch mode's scale and an oversampling override in it, so the owner decides how sharp the UI is by scaling its window; the library follows, including a change of scale that nothing else tells it about (a window moved to another display, the owner changing `contentScaleFactor`): it draws again at the new scale without a commit. `Window.use_font_oversampling = false` (a deliberate 1x raster) is honoured, as it is for Godot's own controls. The snapshot's `oversampling` is the scale the root last drew at.

**An owner that wants a high-DPI window sets one of these; the library does not.** A native window with no stretch settings has a content scale factor of 1: logical pixels are physical pixels, the text is as sharp as the screen, and the UI is small on a Retina display (the demo's 1120 x 800 window is 560 x 400 points on a 2x Mac, `DisplayServer.screen_get_scale()` is 2). To lay the UI out in points and draw it at the display's resolution, set `Window.contentScaleFactor = DisplayServer.screenGetScale()` (what the Web demo owner does every frame, so browser zoom and display changes are followed), or use the project's `display/window/stretch/mode = canvas_items`; either gives the viewport an oversampling of the scale. Injected input (`Input.parseInputEvent`) is in window pixels, which the window divides by the content scale, so a verifier gives it positions in logical pixels times the scale. A root inside a `SubViewport` has the viewport's own scale, not the window's: to render a `SubViewport` (a world-space panel) at more texels than layout pixels, set its `size2DOverride` to the layout size, `size2DOverrideStretch` on, and `size` to the texel size (`docs/WORLD_SPACE.md`).

**Layout and motion utilities.** Margins take `auto`, negative and percentage values; `w-screen`, `h-screen` and `[50vw]` size against the root; `w-fit`, `w-min` and `w-max` size by content (for `width`, `height` and `flex-basis`; Taffy takes no keyword for a minimum or maximum size); grids take `grid-cols-[...]` and `grid-rows-[...]` tracks (`minmax`, `fit-content`, `repeat(auto-fill, ...)`), `col-span-*`, `col-start-*`, `grid-flow-*` and `auto-cols-*`; `content-*`, `justify-items-*`, `place-*`, `order-*`, `aspect-*`, `invisible`, `overflow-clip`, `block`, `flow-root` and `container` work as in Tailwind (`order` changes layout, not paint or hit-test order). `transition`, `transition-colors|opacity|transform|shadow|all|none`, `duration-*`, `delay-*` and `ease-*` use Tailwind's timing and compose across variants (`transition-colors hover:duration-500` keeps the colours and takes 500 ms while hovered); `transition-all` animates every property native can and lets the others jump, quietly. Text colour and border colour animate, and text that inherits a moving colour follows it. Classes with no honest meaning here (`space-*`, `divide-*`, `inline-*`, `float-*`, `sticky`) throw an error that names what to use. Taffy lays the lab out within 0.5 px of Chrome's on every edge of 582 boxes at two window sizes, and the transitions are held to Chrome's curves (`docs/tracks/utilities-layout-motion.md`). `docs/tracks/tailwind-coverage.md` measures which of Tailwind v3.4.17's classes compile; it was generated before the paint utilities merged and still counts shadows, rings, outlines, per-side borders and corners and gradients as missing, so regenerate it (`scripts/tailwind-coverage.mjs`) before quoting its totals.

**Text utilities.** `font-thin` to `font-black`, `italic`, `font-sans|serif|mono` and `font-['Name']` choose a face from the families registered with `registerFontFace(root, { family, weight, style, font })` (CSS font matching: the nearest weight, an italic face when the family has one, a slant or a thickening made up when it does not; a variable font's `wght` axis draws any weight in its range). Text that names no registered family keeps the theme font, so a tree with none of this costs nothing. `text-sm` and the other sizes carry Tailwind's line heights; `leading-*`, `tracking-*` (fractions of a pixel are exact), `uppercase|lowercase|capitalize`, `underline|overline|line-through` with `decoration-*` and `underline-offset-*`, `truncate`, `text-ellipsis`, `line-clamp-1` to `6`, `whitespace-*`, `break-normal|words|all`, `text-justify` and the numeral classes compile to longhands and render as Chrome renders them, to within a pixel (`docs/tracks/utilities-text.md` has the numbers and what differs). Unset `white-space` behaves as `pre-wrap`, as React Native's `Text` does. `antialiased` compiles to no style, because the library already draws the lighter look of Chrome's `-webkit-font-smoothing: antialiased` (Chrome's default smoothing puts down 12.7 % to 15.2 % more ink than ours); `subpixel-antialiased` throws. The demo registers Open Sans, PT Serif and JetBrains Mono (SIL OFL 1.1; `demo/fonts/`).

**Shadows, rings, outlines, borders by side, gradients.** `shadow-*` (`shadow-sm` to `shadow-2xl`, `shadow-inner`, `shadow-none`, `shadow-<colour>[/<opacity>]`, `shadow-[<css>]`), `ring-*` and `ring-offset-*` (with `ring-inset`), `outline-*`, `border-{t,r,b,l,x,y}-*`, `rounded-{t,r,b,l,tl,tr,br,bl}-*`, `bg-gradient-to-*` with `from-*`, `via-*` and `to-*` (colours, opacities and positions) and the inline `boxShadow`, `backgroundImage`, `border<Side>Width|Color`, `border<Corner>Radius` and `outline*` styles compile as Tailwind v3 does and draw as Chrome draws them: a shadow is a Gaussian of the box's own rounded rectangle, cut out of the box when its background lets the backdrop through (a frosted panel does not show its shadow), a ring is a shadow with a spread, an outline replaces the native focus ring, a border can have a different colour and width on each side with mitred corners, and a gradient is interpolated in sRGB with premultiplied alpha along CSS's own gradient line. Shadows and rings compose across variants (`shadow-sm ring-1 focus:ring-2` keeps the shadow when the ring grows) and `boxShadow` is a native transition property. Against headless Chrome at device pixel ratios 1 and 2, on the Compatibility, Mobile and Forward+ renderers, on Breaka's and the stock engine and in the Web build, a page of any of these differs by under a level on average and by at most a few levels on shadows, rings, outlines and gradients; the arcs of a plain rounded box and the ends of one-sided borders on a curve differ by up to a quarter of the contrast on a pixel or two (`docs/tracks/utilities-paint.md`). A tree with none of these pays nothing for them.

**Transforms.** `transform` and `transformOrigin` take CSS text (Stylo parses and validates it, so units, `calc()` and every syntax rule are the browser's), and Tailwind's `translate-*`, `rotate-*`, `skew-*`, `scale-*`, `origin-*` and `transform` utilities compose across variants as they do in Tailwind 3.4. An element is moved by giving its canvas item the matrix, so layout is untouched and nothing is re-recorded; hit testing, `getRect()` (the bounding box, as `getBoundingClientRect()`), the focus ring, text selection and the text input caret, wheel and touch scrolling, drag and its ghost, accessibility bounds, filter extents and `scrollIntoView` all go through it. Transitions and `starting:` animate the matrix with Stylo's own interpolation (matching lists function by function, others by decomposing the matrices) and agree with Chrome's to a fraction of a pixel. Text and rounded corners are rasterised at the scale the transforms put on them (again once an animation settles). A transformed element is the containing block of its `absolute` and `fixed` descendants, as in CSS. Boxes under a rotation, scale, skew or matrix, square or rounded, with any borders and gradients, are drawn from antialiased triangles with a feather per axis (`docs/tracks/box-mesh.md`), so a squeezed edge keeps a one-pixel ramp and a rounded card turned or scaled is within a few levels of Chrome's; a box with no transform, or only a translation, is drawn as before and matches a Godot `Panel` pixel for pixel. `starting:` is CSS `@starting-style`: its layer is the style a node starts from, on mount or when it is shown from `display: none`, and the node transitions from it. Not built: `perspective` (refused with a message that says so) and `transform-style: preserve-3d`; `rotateX` and `rotateY` are drawn flattened, as CSS draws them with no perspective (3D was assessed and not built; "Current limits"). Rotated and skewed `overflow` clips are not exact ("Current limits"). `docs/tracks/transforms.md` has the Chrome comparison.

**Filters and frosted glass.** `filter` applies CSS filter functions to an element and everything painted inside it (`blur`, `brightness`, `contrast`, `grayscale`, `hue-rotate`, `invert`, `opacity`, `saturate`, `sepia`, and one `drop-shadow`); `backdropFilter` applies them to what is already drawn behind the element, inside its rounded border box, which is frosted glass: React siblings, the main layer under a `Portal` scrim, and Godot content behind the root, 2D and 3D. Both are built from engine primitives (a copy of the render target and a mip-reading material for the backdrop, a canvas group for the filter), on the Compatibility renderer (the default, and the Web), and on the Mobile and Forward+ renderers, each measured on its own (Forward+'s back-buffer chain is a different, wider filter than the other two's, and the two RenderingDevice renderers place a level's texels by the whole target, not the copy region); any other rendering method draws nothing and logs one error. `blur(r)` is a Gaussian of standard deviation `r` logical pixels, scaled to the render target; on a hard edge the verifier holds its profile within 0.02 of a true Gaussian's and its width within the larger of 4 % and 0.6 px (the model predicts under 0.01). Separate Tailwind utilities compose across variants, so `blur-sm hover:brightness-110` keeps the blur on hover and `hover:backdrop-blur-lg` changes only material parameters, with no React work, commit, layout or re-record; an inline `filter` replaces the whole list. Both transition (`transition: { properties: ['filter', 'backdropFilter'], ... }`), function by function. An element without a filter, and a tree without any, create no item, material or shader. A frosted panel or filtered element costs roughly 0.5 to 2 ms per frame on an Apple M1 Max at 1120 x 800, nearly flat in size and radius (measured on Compatibility and Mobile; Forward+ cost was not measured; `docs/tracks/filters.md`, "Cost"), and the first use of each shader compiles it (about 50 ms on Compatibility; 0.8 to 1 s on Mobile with a cold shader cache, 17 to 36 ms with the engine's disk cache). Nothing warms the shaders up automatically, so a loading screen may show a 1 x 1 `backdrop-blur-sm` element (and a 1 x 1 `blur-sm` one for `filter`) to pay that early. Limits: an element can have both `filter` and `backdropFilter` (`backdrop-blur-xl drop-shadow-lg`): its backdrop is drawn beside its group, not in it, so unlike CSS the filter does not apply to the backdrop's result (a drop shadow is cast by the element's own fill, not by the frosted area, and shows through a translucent fill); on Compatibility and Web a group's buffer is the opaque render target's RGB10_A2 back buffer, so alpha inside a filter group has four levels (a half-transparent filtered element is drawn at a third or two thirds); a `filter` inside a `filter`, or a `backdropFilter` inside a `filter`, is reported once with an `ERROR` and not drawn (Godot's canvas groups do not nest); the colour functions of a list are composed into one matrix after the blur, so values that leave 0 to 1 between two functions are not clamped between them as a browser does; a list has at most one `drop-shadow()` and no `blur()` after it, and `backdropFilter` has none; `backdrop-filter: opacity()` blends with the unfiltered backdrop, not with the page; a blur is capped by the render target's mip levels on Compatibility (a 600 x 900 window reaches about 50 px, a 1120 x 800 one 64 px and more; the snapshot's `effects` plan says what was drawn and `clamped` when less), and on the RenderingDevice renderers a target that does not halve exactly (600 x 900, 1366 x 768) makes the last steps up to 4 to 5 % wider at 600 wide; `url()` filters, `em`/`rem` lengths and `position: fixed` descendants of a filtered element (they paint in the root, outside its group) are not supported; an ancestor's clip keeps its own pixels, so content beyond the clip is absent from the blurred picture and fades at the clip edge; a root in a `SubViewport` sees only that viewport's contents; a rotated or unevenly scaled root blurs by its mean scale; a blur near the render target's edge reads the edge texels again where a browser blurs the part beyond the window (let a blurred background bleed past the window instead of ending at its edge); a drag ghost shows a filtered source unfiltered; a scrolled `TextInput`'s own text overflow is not in its filter group's extent; a render target with a transparent background (a `SubViewport` with `transparent_bg`) has not been measured, so frosted panels over one are not claimed to work.

The palette is all 22 Tailwind v3 colours, shades 50–950, plus white, black, and transparent, as sRGB hex values; any of them takes an opacity modifier (`bg-white/20`, `bg-sky-500/30`). A frosted-glass page as a developer would write it (`backdrop-blur-xl backdrop-saturate-150 bg-white/20 border border-white/30`) is the demo's `glass` lab (`demo/src/glass-lab.tsx`), and `docs/tracks/filters.md` ("Glass showcase") compares it with the same CSS in Chrome. Breakpoints use the surface's logical width, not physical display pixels. [Style types](src/types.ts), the [native protocol](native/PROTOCOL.md), [motion architecture](docs/MOTION_ARCHITECTURE.md), and the [Blitz/Stylo evaluation](docs/BLITZ_EVALUATION.md) document the supported surface and boundaries.

## Architecture and performance boundary

React 19.2.0 matches the backend's version; `react-reconciler` 0.33.0 is pinned to its compatible peer contract. React is a peer dependency so the application and renderer share one instance. Native dependencies are `godot` 0.5.5, Taffy 0.15.0 (git revision `fca167c`), and `blitz-dom` 0.3.0-beta.4 (git revision `3f85506`, retaining Stylo 0.23.0 for CSS transition resolution), locked by Cargo. The native builds are bound to the Godot 4.7.2 API (`native/api/stock-4.7.2`) and loaded by Breaka's 4.8 as well as by stock 4.7.2; the `breaka` profile's Web build is bound to the exact API exported from the project's Godot 4.8 binary and the `stock` profile's Web build to the 4.7.2 one, all recorded in [native/api](native/api/README.md). The demo's bundles contain the production builds of React and `react-reconciler`; the renderer registers with the React DevTools hook (as production bundle type 0) when a page installed one, and the demo's code editor keeps component state across an edit through stable family proxy components instead of `react-refresh/runtime`.

The architecture is React Native Fabric's, end to end (`docs/INTERACTION_PLAN.md`). The reconciler runs in persistent mode: during render it creates and clones lightweight, immutable JavaScript instances that share unchanged children, and it makes no native call, so abandoned concurrent renders cost nothing natively. At commit, a pure walk (`src/commit.ts`) finds the changed nodes by instance identity (an instance identical to its committed one skips its whole subtree) and sends **one `commit(layer, payload)` call** carrying only the created nodes, the prop diffs and the changed child lists. Native validates the whole payload before changing anything, diffs each changed child list (longest increasing subsequence for moves) into a mounting transaction, applies it to a mounted tree keyed by `u32` tags that JS allocates, resolves computed styles for the nodes whose inputs changed, lays out with Taffy's retained tree, updates geometry only where it changed, and re-records only the canvas items whose visuals changed. Event closures stay in JS, while native input queues are drained outside mutable Rust calls. The persistent shadow tree lives in JS rather than behind native handles because GodotJS cannot make V8 account for native memory behind wrappers (decision D2 in the plan).

Taffy owns Flexbox/Grid geometry. Godot `TextParagraph` owns text shaping and intrinsic measurement. Stylo (via `blitz-dom`) owns transition timing, easing, interruption, and reversal on the native process clock, while a dedicated native measurement tree supplies intrinsic endpoints when `interpolateSize: 'allow-keywords'` is active. A single custom `Control` owns a retained hierarchy of lightweight `RenderingServer` `CanvasItem` RIDs that mirrors the view tree (a box item and a clipping content item per element), with rectangular clipping (`overflow: 'hidden'`) for both rendering and hit testing; there is no Godot `Container` or `Control` for every React element. Moving an element changes one transform, an opacity change one modulate, and only an element whose own visuals or size changed re-records. A plain box is one `StyleBoxFlat` call; shadows, rings, outlines and the sides of a border are baked coverage masks drawn as tinted nine-patches and shared between boxes with the same layer, gradients are meshes over a baked one-pixel ramp, and a box under a transform is a feathered mesh (no per-element material anywhere: materials break batching, and the Compatibility renderer on the Web draws nothing past 16 per-instance shader parameters). A `Text` with nested `Text` is one node whose spans are flattened in the renderer's host config (`src/rich-text.ts`) and drawn per glyph over one shaped paragraph. Each `<Portal>` has its own container in the overlay layer. Paint and layout invalidation are separate. Snapshots and opt-in profiles expose node geometry, computed styles, active transitions, commit counters (`nodesCreated`, `nodesUpdated`, `mutations`, `boxRecords`, `contentRecords`), and commit, layout, paint, and stage timing counters.

Measured on Chrome 156 (debug template, development React, which is from before the demo bundled production React; a heavily swapped Mac; `node scripts/verify-motion-web.mjs --acceptance`, figures in `docs/INTERACTION_PROGRESS.md`, Phase F4): changing one cell's colour costs the native `commit` 0.17 to 0.20 ms at 50 and at 2,000 cells (the previous renderer: 0.79 ms and 11.7 ms), with one mutation and a 216-character payload at both sizes. Hovering and resizing across a breakpoint cause no React commit and no commit call; a 200-move hover sweep over 2,000 cells re-records two boxes per move. Updating all 2,000 cells takes about 52 ms (previously 57 ms of reconcile plus draw) and an idle frame records nothing. React still walks a parent's children when one child changes, so one change under a flat parent of 2,000 siblings costs 18 ms of JavaScript (4 ms with memoized cells) against 1.8 ms when the same cells are grouped in rows of 50; group large lists.

This remains a performance prototype: the commit payload is one JSON string per commit, a parent of many siblings is still copied by React when one child changes, intrinsic-size transitions clone the Taffy tree to measure an endpoint, and Taffy rounds its whole layout after each layout pass. It does not claim zero allocation or a frame-rate guarantee. Custom GodotJS/V8 hooks are intentionally deferred until measurements identify a bridge bottleneck; GodotJS already supplies the scheduler and ClassDB facilities required here.

The Web verifiers serve the export themselves, on a free port that only they know, and stop the server when they finish: run them with no server and no port. `pnpm demo:web` is only for looking at the export by hand (port 8096, or a free port if that is taken; `--lab=<id>` opens a lab). `GODOT_REACT_WEB_URL` names a server you started: the verifier then fetches every file of the export's receipt from it and refuses to open a browser unless each is byte for byte the export it checked (another checkout's, the other engine's, an older side module under the same pack all fail). Web uses the browser's JS runtime through GodotJS and the Rust extension compiled to a Wasm side module. It requires the matching threaded GodotJS templates and Emscripten/lazy-table ABI described in that guide, plus its separately pinned Rust nightly.

**Web hosting (react.breaka.club).** The release Web export (`node scripts/build-web.mjs --release`) is a stripped pack: 30 files, 6.6 MiB, with no source maps and none of the verification or probe scripts (the Web verifiers use the debug export, which is unchanged). `pnpm deploy:web:plan` stages and compresses it and prints every file and what would be uploaded; `pnpm deploy:web` compresses each file once with brotli, publishes an immutable release under `react-demo/v2/` in the `breaka-asset-uploads` bucket (a manifest and content-addressed objects) and then moves a single pointer object, and deploys the Worker (`deploy/cloudflare-worker.ts`, `wrangler.react-demo.jsonc`) only when its source changed. The Worker serves the current release's page with `no-cache` and an ETag, so a deploy is picked up on the next visit and an unchanged page costs a 304; the page's `<base href="/r/<release>/">` points every relative load of the engine at one release, the large `.wasm` and `.pck` files answer there with a cacheable redirect to `/o/<hash>/<name>` so a binary that did not change between two deploys is already in the visitor's cache, and everything under `/r/` and `/o/` is `public, max-age=31536000, immutable`, sent as the stored brotli (`Content-Encoding: br`) when the browser accepts it. The bare address redirects to `/?demo=navigator`, and every response, redirects and errors included, carries `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: cross-origin`, which the threaded engine needs. A cold visit transfers about 12 MiB (it was 66.6 MiB, 52.7 MiB of it the uncompressed pack) and a returning visitor after a deploy about 2 MiB, measured in headless Chrome through the Worker on `wrangler dev` with a browser that accepts only `br`. `pnpm deploy:web:releases` lists the releases the site has shown and `pnpm deploy:web:rollback` points it back at the previous one in a single object write; `--local --persist-to=<directory>` runs a deploy against wrangler's local R2 state. `pnpm check:site --url=<address> --files` loads a site in headless Chrome, compares every file with the export's receipt, and opens the navigator, a lab and the code panel. See [docs/tracks/web-deploy.md](docs/tracks/web-deploy.md) and [docs/tracks/web-load.md](docs/tracks/web-load.md) (which has the measurements, the rollback commands and why brotli rather than zstd).

The Web interaction verifier sends Chrome wheel events, and Godot's Web display server makes a pixel delta of `d` into `0.03 * d` wheel ticks, so a 100 px notch is 3 ticks at device pixel ratio 1 and 1.5 at 2 (a native notch is one); a check that scrolls must expect that (`notchTicks()`). Console errors a section provokes on purpose are announced with `expectedConsoleErrors` and must appear, and the portrait navigator keeps its labs in a menu whose items exist only while it is open (`docs/tracks/web-fixes.md`).

Where each phase's verifiers, counts and captures were recorded is `docs/INTERACTION_PROGRESS.md` (one section per phase and per track); the results of the full regression run for final acceptance go in its "Final acceptance" section, and those of the batch since in its "Batch regression" section. Web verification is real Chrome through Puppeteer, at device pixel ratio 1 and 2, in landscape and portrait, with a touch page, against the debug template of Breaka's engine; the `stock` profile also ran its debug and release templates. On Breaka's engine the release export ran `verify:web --release`, `verify-live-compile-web.mjs --release` and the landscape pass of the navigator section; the rest of the interaction verifier ran against the debug export. Safari, other browsers and mobile devices have not been qualified.

When Godot's Web shell (`fetchWithProgress`) finishes reading `index.pck` through `ReadableStream.getReader()`, Chromium can emit a benign `net::ERR_ABORTED` on the completed stream close after all `Content-Length` bytes are delivered; `verify-motion-web.mjs` verifies the exact byte count and SHA-256 of `index.pck` before allowing that post-completion event. The verifier also records the existing Emscripten dynamic-loader synchronization warning once before startup and treats all other runtime errors as failures.

## Current limits

This is the plan's non-goals (`docs/INTERACTION_PLAN.md`, 2.3) plus everything the decision log and the track notes record as not done, not fixed or not verified, each checked against the code at final acceptance and, for the tracks since (the utility classes, transforms, rich text, the combobox, the code editor and live compile, Web hosting, the single native build), against their notes. Anything not listed here is built. Details: [native/PROTOCOL.md](native/PROTOCOL.md), [docs/WORLD_SPACE.md](docs/WORLD_SPACE.md), [docs/tracks/](docs/tracks/).

**Not built, on purpose (the plan's non-goals).**

- A JSI-style binding that bypasses GodotJS's method marshalling (revisit only if measurements show the GDExtension call boundary is the bottleneck).
- A Godot `Control` per element, including `LineEdit` and `TextEdit`; a custom engine module (a proven Web engine bug is fixed in the engine's `platform/web`, not by an export-time patch).
- Drag and drop with other Godot `Control`s (`_can_drop_data` is synchronous on `&self`, where a JS answer cannot be had; `endedOutsideRoot` plus the release point is what a game uses).
- Raw text outside `<Text>`, `contenteditable`. (Rich, nested text runs are built: "Rich text".)
- CSS stacking contexts: `zIndex` orders the siblings of one paint parent, as in React Native.
- Touch text-selection handles, long-press menus, native context menus, spellcheck.
- Animated programmatic scrolling, overscroll bounce, `position: sticky`, rounded clip masks (clipping is rectangular; border radius changes paint, not the clip), native list virtualization. (2D transforms are built; 3D is recorded below.)
- Pen-specific pointer data: a pen is reported as a mouse.

**Not built, recorded.**

- *Styles.* There is no DOM, full CSS cascade, selector engine or Tailwind plugin support; this is a strict subset and the compiler throws on what it does not know. Still rejected, as the track notes and the audit record them: `space-*`, `divide-*`, `float-*`, `clear-*`, `columns-*`, `inline`, `inline-*`, `table*`, `contents`, `list-item`, `sticky`, `isolate`, `collapse`, `min-w-min` and the other intrinsic keywords on a minimum or maximum size, `max-w-prose`, `calc()` in a size, `grid-cols-subgrid` and `content-baseline` (each throws with a message that names what to use); `animate-*` and general `@keyframes` animations or animation callbacks; images (`bg-size`, `bg-position`, `bg-repeat`, `object-*`, `url()` and radial or conic gradients) and custom materials; dashed, dotted and double `border-*` and `outline-*`; logical sides (`border-s`, `rounded-ss`) and the `*-opacity-*` classes (use an opacity modifier on the colour); `text-wrap` and `text-balance`, `hyphens-*`, `indent-*`, `align-*` (vertical alignment), `font-synthesis` and `subpixel-antialiased`; `perspective` and `preserve-3d`; and the variants `dark:`, `group-*:`, `peer-*:`, `first:`, `odd:`, `before:`, `print:`, `motion-reduce:`, `max-*:`, `aria-*:` and `data-*:`. `break-keep` is accepted and does nothing. Grid has tracks and a line or span per item, not template areas or subgrid. Both overflow axes clip together (`hidden`, `scroll` or `auto` on either clips the padding box). Mixed pixel and percentage transitions, and intrinsic transitions on a flex main axis whose `flexGrow` and `flexShrink` are not zero, are rejected when the commit is validated if a `transition` names the property; under `transition-all` they jump quietly, and a style change native itself causes (a hover, a breakpoint) that would need one is applied without animation and logs an `ERROR`. `transition-all` animates the properties native can (sizes, opacity, colours, filters, transform, box shadow): padding, margin, gap, insets and radii jump.
- *Layout utilities.* `w-min` on a wrapping flex container gets the narrowest width but one line of height (Taffy); `flex-1` in a column of unknown height shares the container's height by the boxes' own heights where Chrome takes the content; a flex-shrunk box with an `aspect-ratio` keeps the height of its unshrunk width; `order` changes layout, not paint or hit-test order; there is no inline layout, float or table layout, and viewport units resolve against the root's size.
- *Text styles.* The utilities do nothing on a `TextInput`, which shapes with the theme font. A word that ends within a space width of the line's end wraps one word early (about one line in sixty). A baseline can be a pixel lower than Chrome's (FreeType rounds the ascent up where Chrome rounds hhea), and a centred line sits on a whole pixel, up to a pixel from Chrome's. Underlines are whole where Chrome breaks them round descenders. Glyphs from a fallback font are not tracked and can make a line taller. Text wider than its box is cut at the box where CSS lets it overflow, and an unbreakable word in wrapping text is not ellipsised. Offsets JS sees count the shown text when a transform or white space changes its length.
- *Rich text.* A span takes colour, background, family, weight, style and decoration only (no size, letter spacing, case or numerals), an inlay holds plain text, and a nested `Text` has no ref, handler, `role`, `testID`, state class or breakpoint class. Caret positions are by line box: a mixed-direction line has two carets at a direction change and `getCaretRect` answers the primary one; bidirectional text and a span that splits a grapheme cluster were not compared with Chrome. `auto` thickness on dotted and dashed lines, dash positions between device pixels and the round dots of a 4 px dotted line differ from Chrome's. The demo's fonts have no CJK glyphs, so such characters take their room and draw nothing in a span.
- *Shadows, borders and gradients.* Borders, radii and outline widths are whole logical pixels in paint (layout takes the float). A gradient is laid out over the padding box and drawn under the border; beyond it, it holds its end colours where CSS tiles the image, which shows only under a translucent border. The corner arcs of a plain rounded box (one `StyleBoxFlat` call) sit 0.3 to 0.5 pixel inside Chrome's at 45 degrees. The first draw of a shadow bakes its mask on the CPU (1.7 ms for `shadow-2xl` at device pixel ratio 1, 6.5 ms at 2; a transition of `box-shadow` bakes the masks of each frame, which was not measured in the engine).
- *Transforms.* `perspective`, `transform-style: preserve-3d` and `backface-visibility` are not built. An experiment (`docs/tracks/transforms-3d-feasibility.md`, nothing under `native/` changed) shows that a transformed element with its subtree rendered into its own render target and drawn as one canvas item with a homography shader matches Chrome (interior mean difference 0.01 to 0.13 levels of 255 for perspective, 0.9 to 1.6 for `preserve-3d` cubes and intersecting planes, 1.1 to 1.3 for nested surfaces, on both engines and all three renderers); the Rust implementation is estimated at about 4,000 lines and six weeks, and the Web (WebGL2) was not run. An `overflow` clip in a frame that a transform rotates or skews is drawn as the box round the rotated rectangle, with one `ERROR` per element (hit testing is exact); translate, scale, mirror and quarter-turn clips are exact, and an exact rotated clip needs a render target per clipped element. Scrollable overflow ignores transforms, `touch-action` axes are screen axes, `zIndex` makes no stacking context for a transform either, a `relative` element between a transform and a `fixed` descendant is that descendant's containing block here and in CSS it is not, and the blur radius of a `filter` is not scaled by a transform on it. A border whose sides differ in colour, an outline and a shadow ring (baked masks) and the focus ring (a `StyleBoxFlat` stroke) keep one feather length, so under a squeeze their edges are not antialiased per axis. While a transform transition runs, a box and its text keep the drawing they had and are drawn again when it settles (a cost proportional to the subtree). What is left of the difference from Chrome on `rotateX` and `rotateY` at device pixel ratio 2 is Chrome's own resampling of a squeezed layer.
- *Scrolling.* Scrollbar track clicks (paging), pull to refresh, snap points. A wheel or pan gesture chains from one container to the next event by event, with no latching.
- *Select.* Radix's press-drag-release, item groups and separators, `position="item-aligned"`; moving the pointer over an item cut by the list's edge focuses it and scrolls it into view (`focus()` has no `preventScroll`). A prevented press is never a pan (D33), so a kit part that prevents a press to manage focus loses touch scrolling unless it exempts touch, as the `Select` and `Combobox` lists do; a finger that begins a swipe on a `Combobox`'s clear or trigger button or on a chip's remove button (they prevent the press so as not to take focus from the input) cannot pan the page.
- *Combobox.* No virtualisation and no `items` prop: a thousand options cost what a thousand `Select` items cost, and a keystroke over that many re-renders them all. The platform accessibility tree for it was read once on the `stock` profile and no expectation was written from the reading, and the live region of `Combobox.Empty` is not in the lab.
- *Text selection.* Word-granularity dragging after a double click (in a `TextInput` it exists), caret affinity at wraps and direction changes, highlighting a selected line break, auto-scroll while selecting.
- *TextInput.* Native IME has not been checked by hand with a macOS Japanese or Pinyin input source (the Web IME was driven through Chrome's CDP). Engine behaviour that stays: the engine's IME start drops the last queued raw key; after a Web composition ended by a focus move `ime_started` stays set and raw keys are dropped until one more composition commits (an engine bug, to be fixed in the engine); the Right presses of two keys in one frame add up, so a text typed in a hurry into the middle of a field leaves the native caret too far right, and the caret after JS puts an edit back mid-text is off until the next key. A click inside a composing input cancels the composition without committing it. `clipboard_get` on Web returns what the previous call read, so anything else that calls it is still stale (the root's own paste no longer does). The IME window and the on-screen keyboard are placed from the root's own screen transform, which is wrong for a root on a quad in a `SubViewport`. `multiline` cannot change after creation. A triple click selects all of a text area's text, not a line.
- *Drag and drop.* Files and `setDragImage`. The ghost of a filtered source is unfiltered, and it does not follow a change of display scale mid-drag.
- *Accessibility.* `aria-labelledby`, `aria-describedby`, `aria-haspopup`, `aria-pressed` and `aria-invalid` are not typed or sent (`aria-activedescendant` and `aria-controls` are); tooltip text and its action; list and tree item counts and positions; a numeric step; `aria-live` is sent but untested. Each scroll re-sets every exposed descendant while a screen reader is attached, instead of moving one content element as `ItemList` does. The engine cannot convey a group or radio-group element, a mixed checkbox, a text area's value, a read-only field, or a scroll view's position and actions to the macOS adapter (recorded as `GODOT_REACT_A11Y_GAP`; scroll bar elements carry the position).
- *Display scale.* `CanvasItem.oversampling_with_scale` (a root whose own `scale` is above 1 draws at the viewport's level). Glyph caches at levels no viewport owns are not freed: about 20 MiB after drawing at levels 1, 2 and 3 (in use there are two sets, bounded, freed with the font). Layout and borders round to whole logical pixels.
- *World space.* No occlusion test, one quad per owner, back faces take no input, pan and magnify gestures, joypad and `ui_*` focus navigation are not forwarded, the cursor shape is not applied, hover is not re-tested when the quad or camera moves without the mouse, and the anchored label is not clamped to the window (`docs/WORLD_SPACE.md`).
- *Engine behaviours not worked around.* A trackpad pan gesture reaches Godot's `Input` twice, so JS gets two `wheel` events for one pan (and Godot's own `ScrollContainer` scrolls twice); Godot's Web display server maps a DOM `deltaX > 0` to `WHEEL_LEFT`, so horizontal wheel ticks have the opposite sign on Web; on Web a touch's `pointerId` is the browser's contact identifier, which keeps counting across taps, not `2 + index`; GodotJS's V8 has no `Intl`, so libraries that need it need a polyfill natively.
- *Platforms.* The native addon manifest, the live-compile extension's and the quiet verifier windows target Apple Silicon macOS only; other platforms need manifest and build work and runtime qualification.
- *Builds.* The freshness guard does not cover the Rust and Emscripten toolchains beyond `rust-toolchain.toml`, the engine, the compiled JavaScript or the tracked `demo/typings`. The native builds are bound to Godot 4.7.2 and an older engine is refused; Breaka's 4.8 resolves the methods the library calls on first use, so a method missing from its class table would fail at its first call.
- *The code editor and live compile (demo only).* Completions are not built; hover is the name and the type (no documentation text, types printed with qualified names) and inlay hints are parameter names and the inferred types of variable declarations (no inferred return types, callback parameter types or object property names). A render that throws loses the state of the tree that threw (React discards it): the last good version renders again from its first render, and the class check only covers a mistyped literal `className`. Only the files of the lab's project can be edited, the project is the labs' TSX plus the declarations of the library, React and the ES2022 lib files (a lab that imports anything else gets TS2307), `import.meta` and top-level `await` are diagnostics, and leaving a lab drops its edits. Moving up and down keeps the column in code units, so over a line with wide characters the caret lands by code unit, not by x. The extension needs a Bun checkout for its vendor step and its own Rust nightly, and its Web side module is built for the `breaka` profile only and adds about 2.3 MiB (brotli) to a cold visit though nothing uses it until the code panel opens (loading it on first use was designed, not built).
- *The lab navigator.* It is not shown in a window narrower than about 300 logical pixels, and most labs were written for 560 and wider; a window or scene lab is not shown inside it; the error panel shows the stack with its absolute file paths; the Filters explorer offers eight of the verifier's fixtures; the Events lab's danger buttons blank the window for 600 ms before the navigator returns on the same lab with its state reset.
- *Web hosting.* The bucket is never pruned (old releases stay so open tabs keep working); a cold visit pays one extra round trip for the redirects of the large binaries and the bare address's redirect is `no-store`; the page's progress bar counts the pack and the engine module, not the side modules; `main.js` still carries the verifiers and CodeMirror (sharing and trimming them would save about 0.36 MiB of a 12.2 MiB first visit); Cloudflare Web Analytics injects its beacon (a zone setting).

**Not verified** (built, but not shown to work in the way a user would meet it).

- Native IME and VoiceOver by hand; platform focus (the verifier's window is not the key window, so the accessibility run skips it); the actions on a text field through a real adapter (the dump tool performs none).
- The platform accessibility tree on Breaka's engine, which has no accessibility driver: `pnpm verify:a11y` runs the Godot-side half there and ends "not verified" (exit 2). The macOS tree was read on the `stock` profile only. Windows (UI Automation) and Linux (AT-SPI) trees were not read, a reversed scroll axis and `scrollbar-width: none` were not read in the real tree, and the Web engine has no accessibility code.
- The kit controls and positioning have no Web verifier section of their own (the Web interaction verifier has none for `inputs` or `positioning`), so touch on the kit `Slider` was not exercised by a verifier (the lists of `Select` and `Combobox` are, in `dropdown-touch` and `combobox`). The world-space anchored label is verified natively only. IME and on-screen keyboards through a `SubViewport`, and a `SubViewport` that updates only when visible, were not exercised.
- Filters: a render target with a transparent background (a `SubViewport` with `transparent_bg`) under a frosted panel; the GPU cost on Forward+, and the cost on Web; the engine's truncation of a group's negative region, whose fix is unit-tested but did not reproduce on a real renderer.
- Whether headless Chrome reaches the system pasteboard, and the engine's own last step onto the Mac's pasteboard, because measuring writes to it (verifier runs never touch it).
- Safari, Firefox and real mobile devices. The Web touch pages (forms, combobox, dropdown lists, the code editor) are headless Chrome with emulated touch and the engine's hidden input element, so what a phone's soft keyboard does when focus moves inside a touch (iOS Safari may close and not reopen it), its autocorrection and Android's composing text were not seen; the release Web export on Breaka's engine ran only what "Verification and Web" lists.
- The single native build on Breaka's engine: a library bound to 4.7.2 resolves each Godot method on first use in 4.8, and only the navigator, live-compile, code-editor, rich-text, transforms and paint sections ran on both engines with it (and `paint` again after the last rebase); the batch regression in `docs/INTERACTION_PROGRESS.md` is the check for the rest. Builds with `--probe` and `--faults` were not made for the single-build track, the stock profile's Web build and Web verifiers were not run with it, and `pnpm dev` and `gen:types` were exercised only through the shared refusal code.
- Rich text: the stock engine's Web export; a real high-density display (the Web's ratio 2 is puppeteer's emulated scale); right-to-left text; the platform accessibility tree of a text with spans (the accessible name was read from the snapshot).
- The code editor and live compile: a real IME and a real soft keyboard (the composition events are synthesised), native at device pixel ratio 2 (the Web retina page covers the grid, the caret and the waves at that scale), the machine's real clipboard on the desktop (the section uses the root's in-process one), Safari, Firefox and iPad, and a line with CJK glyphs (none is registered in the demo, so the geometry is verified and the glyphs are not on screen).
- The stock engine's release export was not built.
