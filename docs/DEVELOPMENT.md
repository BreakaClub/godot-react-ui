# Development

How to build, run and verify this repository. The library's own API is in [AUTHORING.md](AUTHORING.md) and [STYLES.md](STYLES.md).

## Run the native demo

These steps are written for Apple Silicon macOS, the platform the demo and the verifiers run on. The demo needs a Godot with GodotJS on V8 and camel-cased bindings: stock Godot 4.7.2 with upstream GodotJS (`--engine=stock`) or Breaka's own Godot 4.8 build (the `breaka` profile, the scripts' default, which is not public); both load the same native build ("Engine profiles and installed builds"). It also needs Node.js, pnpm 11.5.2 and rustup: `rust-toolchain.toml` pins Rust 1.99.1, and the build scripts call rustup's Cargo, not a Cargo that comes first on `PATH`. The demo is also hosted at [react.breaka.club](https://react.breaka.club), the Web export served by a Cloudflare Worker ("Web hosting" below).

```sh
export GODOT=/path/to/godot          # a Godot with GodotJS (V8)
export GODOT_REACT_ENGINE=stock      # unless it is Breaka's 4.8 build
pnpm install
pnpm build:native
pnpm build
pnpm demo
```

`build:native` compiles the optimized Rust library and installs it into `demo/addons/godot-react-ui/bin/`. `build` typechecks before bundling the demo and emitting CommonJS, ES modules and declarations into `dist/`. The demo's bundles contain React and `react-reconciler` built for production (`process.env.NODE_ENV` is `"production"` in `scripts/build.mjs`); `dist/` leaves both as imports. Both package entry points are importable; `pnpm pack` creates a local npm tarball without publishing. Generated GodotJS declarations and scene wrappers are included under `demo/typings/` and `demo/gen/`; `.uid` files are project metadata. Compiled libraries, JavaScript bundles, and the `.godot` import cache are generated locally.

`pnpm demo` opens a **lab navigator**: a sidebar of every lab by group (a top bar with the kit's `Select` below 1024 logical pixels), a filter, a header with the lab's title and description and Previous and Next (also Alt+Up and Alt+Down), and the lab in a clipped, scrolling content area with an error boundary of its own. A lab that needs the whole window (frosted glass) or is its own scene (world space) shows a card and a button for it, with a way back that stays on screen. `--lab=<id>` (`pnpm demo --lab=glass`; `?lab=<id>` on the Web) opens a lab, and an unknown id is an error on screen. The labs are one array, `demo/src/labs.tsx`: adding a lab is one entry (id, title, description, group, how it is shown, its TSX sources). `pnpm demo:web` serves the Web export and prints the address.

**Code editor.** The **Code** button of a lab (not offered below 768 logical pixels, nor for a window or scene lab) reveals that lab's TSX in an editor made of the library's own components: type, and the page above updates after a short pause, with its state kept where the hooks are the same. A syntax or type error leaves the last good page on the stage; type errors, hover types and inlay hints come from Bun's TypeScript checker and compiler, drawn as wavy underlines, inlays, a problems list and a status line. The text lives in CodeMirror 6's headless `EditorState` (Lezer highlighting, history, several selections, CodeMirror's key table); the view is a window of lines, each one `Text` with nested `Text` spans ("Rich text" below) and a caret and gutter; a focused `TextInput` at the caret takes the keyboard, the IME and the soft keyboard and is never edited. The checker and compiler are a separate, demo-only GDExtension, `live-compile/` (its own cargo workspace and Rust nightly; nothing in the package gains a dependency or bytes), built by `node scripts/build-live-compile.mjs` (`--cli` also builds a native test process; `node scripts/build-live-compile-web.mjs` builds the Web side module). Without it the code is shown read-only, with the reason. See `demo/src/editor/` and `demo/src/live-compile-*.ts`.

What a run opens with: `--lab` or `--demo=navigator` opens the navigator, `--demo=app` the single-page playground; with neither, a run that injects its own input (a verifier) opens the playground and every other run the navigator. The Web page's bare address opens the playground (that is what the Web verifiers load), and `pnpm demo:web` and the Worker send it to `?demo=navigator`. The playground has four tabs:

- **Counter:** real React state, derived values, closures, effects, context, disabled buttons, pointer states, and keyboard activation.
- **Inventory:** a responsive Taffy grid, keyed component state, reordering, filtering, insertion/removal, and an empty state.
- **Interaction:** the event pipeline: capture and bubble with `stopPropagation()`, `preventDefault()` that stops native's focus default action, synchronous dispatch (a handler observes native state before its default action runs), `pointerenter`/`pointerleave` that reach only the elements crossed, and handlers that remove their own target, detach the root from the scene tree, or unmount it while native is still inside the press.
- **Motion:** native Blitz/Stylo CSS transitions (`width`, `height`, `opacity`, `backgroundColor`), intrinsic `0 ↔ auto` height transitions (`interpolateSize: 'allow-keywords'`), rectangular clipping (`overflow: 'hidden'`, `'scroll'`, `'auto'`) for both rendering and hit testing, in-flight retargeting across text/font/width/viewport changes, rapid reversal, tree detach/reattach pause/resume, and active-transition removal.

Resize the window to see `md:` classes recompose the layout. Tab and Shift-Tab move between enabled buttons; Enter and Space activate them. All provided Godot launch scripts use `--audio-driver Dummy`.

The demo owner also puts a full-window Godot `ColorRect` behind the React root and counts what reaches it and `_unhandled_input`. The verifiers render pages through `godotReactDemo.showLab(name)`: a HUD over it (`'hud'`: every ancestor is `pointer-events-none`, a few controls are `pointer-events-auto`) to prove that empty space, keys the UI did not use, and wheel ticks it did not consume belong to the game.

## Engine profiles and installed builds

Every build, run and verify script takes the same engine selector, and `breaka` (Breaka's custom Godot 4.8 with its GodotJS) is the default:

```sh
pnpm verify                          # breaka: /Applications/Godot48.app, evidence under artifacts/
pnpm verify --engine=stock           # stock Godot 4.7.2 + upstream GodotJS, evidence under artifacts/stock/
GODOT_REACT_ENGINE=stock pnpm verify
```

`--engine=<name>` wins over `GODOT_REACT_ENGINE`; an unknown name is an error. Each profile has a default `GODOT` path for the machine it was set up on (`scripts/engine.mjs`); `GODOT` overrides either profile's binary; its `--version` must match the profile and be at least 4.7.2.

**The native builds are one build, whichever engine runs them.** The UI library (`pnpm build:native`) and the live-compile extension (`node scripts/build-live-compile.mjs`) are bound to the Godot 4.7.2 API (`NATIVE_BINDING_API` in `scripts/native-binding.mjs`; the dumps are `native/api/stock-4.7.2`), which Breaka's 4.8 loads as well as stock 4.7.2 does: a GDExtension loads in the Godot it was bound to or a newer one, never an older. Each installs over the one path its `.gdextension` names and records the API and the dump hash it was bound to, not a profile; `--engine=` does not apply to them and is refused. Switching between `--engine=stock` and the default needs no build and no install. Breaka's 4.8 resolves each Godot method the library calls on first use (godot-rust's lazy function tables), so a method missing from its class table would fail at its first call.

**What stays per engine profile** is the Web (`pnpm build:web --engine=<name>`, and `node scripts/build-live-compile-web.mjs`, which builds the `breaka` profile only): a Web side module is linked with the Emscripten of the engine whose templates load it, 6.0.12 with Breaka's lazy function-table ABI for `breaka` and 4.0.11 for `stock`, and Breaka's Web side module is still bound to Breaka's own 4.8 dumps (`native/api`); the GodotJS typings (`demo/typings` and `demo/gen` are Breaka's; the stock ones are generated by the stock editor from the one native library into `target/stock-typings`); and the evidence directories (`artifacts/` and `artifacts/stock/`). On Web the `stock` profile uses the stock templates (debug and `--release`; [WEB.md](WEB.md) has the commands).

**After a checkout or a merge, build once:** `pnpm build:native`; `node scripts/build-live-compile.mjs` where the code editor's extension is installed; `pnpm build:web` for each profile in use, and `node scripts/build-live-compile-web.mjs` where the Web code editor is used (`.cargo/config.toml` is an input of every build's digest, so a change to it makes every Web side module stale). A run that needs one of them says so, with the command, before any window opens. The stock typings regenerate by themselves on the next `pnpm test:types --engine=stock`.

**Installed builds are checked against the source.** A build records what it was made from: a SHA-256 of the contents (never the modification times) of `native/` (without its API dumps and Markdown), `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/config.toml` and `build.rs` if present, and the API dump pair it is bound to, plus the cargo features it was built with. It is written into the stamp beside each installed build (`react_ui.build.json`, `react_ui.web.build.json`; a native stamp records the Godot API and the dump's hash it was bound to, a Web stamp the engine profile, and both the probe flag and the library hash), beside cargo's own output in the target directory, and into a Web export's `build-receipt.json` (`extension`). Every script that runs or serves a build compares that with the working tree first and refuses, naming the files that differ and the command that rebuilds: the native verifiers, `pnpm demo`, `pnpm dev` (at startup), `pnpm gen:types`, the Web verifiers and `pnpm demo:web`, the Web export, and `pnpm test:types --engine=stock`, which checks the native library its typings are generated from and never builds it. An installed live-compile extension is checked the same way on every native run (a demo run loads it whether or not its section runs); an absent one is fine, the code editor is then read-only, and only the `live-compile` section is refused. A library or extension bound to another API (a stamp that names an engine profile is a build from before the single build and is one), an engine older than 4.7.2, and a probe build for a default run (nor a `--faults` build, a feature set of its own) are refused too. The refusal comes before any window or browser opens. A Web export's receipt also records a digest of the TypeScript, demo and script sources it was bundled from, the engine template, and each exported file's size and hash; the guard checks all of it, and the fix it names for those problems is `pnpm build:web --export-only`. What the guard does not cover: the Rust and Emscripten toolchains beyond `rust-toolchain.toml`, the engine itself, the compiled JavaScript, and the tracked `demo/typings`; a hand-run `cargo build` changes the library under a stamp that does not describe it (the next `build:native` cleans and rebuilds); and godot-rust's generated bindings follow cargo's own tracking of the API dump's mtime, so a dump restored with an old mtime would not rebuild them (do not edit a dump by hand).

`build:native` and `build:web` do not rely on cargo's own check, which compares modification times and so keeps an artifact when a source is restored to older content with its old mtime. Unless the target directory's stamp says its artifact is a build of exactly the current sources, they run `cargo clean -p godot-react-ui` first (this crate only; the dependencies stay cached), and `build-live-compile.mjs` does the same for its two crates. The first build after the guard was added therefore recompiles the crate once.

For TypeScript iteration, run `pnpm dev`. It watches the demo bundle and opens the Godot editor; run the demo there and restart its scene when changing initialization. Native extension changes require rebuilding and restarting Godot because extension hot reload is disabled. `pnpm dev` refuses to start on a library that is not a build of the current sources; it does not check again while it runs.

## What a PASSED line means

Each native verify script prints a summary after its windows. Read it, not just the exit code:

- `landscape: PASSED` is a run that passed on its first launch. `PASSED (PARTIAL: not run: pointers, drag, …)` is a run that left sections out (`--only=…`; a plain `verify:interaction` runs every default section and is not partial), or checks out (`verify:text-layout --headless` runs no pixel checks; the platform focus check of `verify:a11y` is skipped when the window is not the key window). A partial run is not the verification. `(N recorded engine gap(s), not failures: …)` lists what an engine cannot convey that a verifier recorded instead of failing; `(a disturbance reached its window, but it passed)` says something reached the window and the run passed anyway.
- `PASSED after N disturbed failure(s). First failure: …` is a run that failed, was disturbed by something that reached the window (a real mouse event, a focus loss with a press in flight) shortly before it failed, and passed on a re-run. Its first log and captures are kept (`run-attempt-1.log`, `<window>-failed-attempt-1/`). A failure with no such disturbance is real and is not re-run. `--no-retry` runs each window once: use it for negative controls, where a re-run would hide the failure you are looking for.
- Every window is also refused if the installed library stopped matching the sources since the script started.

A verifier run keeps its own clipboard and never touches the Mac's: native runs hold it in the process's memory (`ReactUiRoot.isolateClipboard(true)`), and `verify:interaction:web` replaces `navigator.clipboard` with an object in the page's memory (no permission is requested). Whether headless Chrome would have reached the system pasteboard, and the engine's own last step onto the Mac's pasteboard, were not measured, because measuring writes to it.

On macOS the native verifier windows never take focus. The engine cannot be asked not to (`show_window` always activates the application), so `scripts/native-run.mjs` loads `scripts/quiet-window/quiet_window.m` through `DYLD_INSERT_LIBRARIES` into automated runs only: the application's activation policy is forced to accessory (no Dock icon), the activation calls do nothing, the window cannot become key or main, it is transparent and click-through, joins every Space and always reports itself visible (the engine stops drawing a window it thinks is covered), and a scene still draws and reads its pixels back (checked on Breaka's engine with the Compatibility, Mobile and Forward+ renderers and on stock 4.7.2 with Compatibility). It fails closed: a verifier run whose log lacks `QUIET_WINDOW_LOADED`, or that logs `QUIET_WINDOW_ACTIVATED` or `QUIET_WINDOW_MISSING`, fails. `node scripts/quiet-window.mjs <godot> [arguments]` does the same for any other Godot command, and `pnpm demo` and `pnpm dev` do not load it, so a person's own window behaves as normal. Other platforms start the command unchanged.

## Editing TypeScript: use an external editor

Godot's script editor does not understand TypeScript. If a `.ts` or `.tsx` file is open in it when the editor saves, it rewrites the file (tabs for the indentation it thinks is wrong: `demo/src/main.ts` came out with 254 changed lines). The scripts that launch an editor (`gen:types`, the import step of `pnpm demo` and every native verifier, the stock typings, `pnpm dev`) take TypeScript out of the project's saved editor layout first (`build:web`'s headless export included), so none is opened by them. That cannot stop you opening a `.ts` file by hand in the Godot editor: edit TypeScript in an external editor, and keep it closed in Godot's.

## Verification

```sh
pnpm test:types
pnpm test
cargo test --locked
pnpm build:native
pnpm build
pnpm verify
pnpm verify:motion
pnpm verify:interaction
pnpm verify:world
pnpm verify:text-layout
pnpm verify:a11y
```

`verify`, `verify:motion` and `verify:interaction` drive real Godot input through the demo at 1120×800 and 600×900, checking state/effects, keyed moves, focus, geometry, paint-only hover, button activation across padding/text, mount/unmount behavior, intrinsic `0 ↔ auto` transitions, pixel-level overflow clipping, in-flight retargeting, rapid reversal, and tree detach/reattach pause/resume, writing PNGs, snapshots, and logs under `artifacts/native/`, `artifacts/native-motion/` and `artifacts/native-interaction/`. `verify:interaction` also asserts capture/bubble order, `preventDefault` on a cancelable event, synchronous dispatch, enter/leave chains and three re-entrant handlers, records the JS time inside one synchronous dispatch, and runs the keyboard lab (Tab order across a reorder, the ring and `focus-visible:` for keyboard focus only, DOM key events and repeats, Enter and Space activation without pointer events, a JS focus trap, `autoFocus`, `focus()`), the pass-through HUD (presses, keys and wheel ticks reach the game exactly when React did not use them, cursors reach the window, `viewportX`/`viewportY` are canvas coordinates), the pointer lab (every mouse button, click counts, a knob that follows a captured drag outside the root, touch taps with the engine's emulation on, two fingers, a cancelled touch, and the root leaving the tree mid-press) and the scroll lab (wheel, trackpad pan, keys, Tab reveal, the scrollbar thumb, chaining and `overscroll-contain`, touch pans with momentum and `touch-none`, clipping pixels, re-clamping, and the counters that show scrolling commits, lays out and re-records nothing) and the drag lab (reordering and moving cards between columns, a trash that takes only `move` and a copy-only source it refuses, effect negotiation and the cursor, a prevented `pointerdown`, a captured pointer and a prevented `dragstart`, Escape, a release beyond the root, the ghost in the raster, edge auto-scroll with the target following the scroll, the root leaving mid-drag, and touch: hold then move drags, a swipe pans). The selection lab adds click, double and triple click, drags across paragraphs past a `select-none` sentence (forwards, backwards and past the end), Shift+click, a Button, captured and prevented presses, copy to the clipboard and select all through the real `ui_copy` and `ui_text_select_all` actions, clearing by a text change or a removal, the highlight's pixels (default and custom colour, under the text, redrawn and cleared) and the highlight scrolling with, and clipped by, its list. Inspect the actual PNGs alongside the assertions.

The other sections: `combobox` (single, multiple and chips: filtering, the keys, placement, a wheel and a press outside, touch on the Web), `dropdown-touch` (the kit `Select`, `Combobox` and `Combobox` with chips pan under screen touch natively and Chrome's touch events on the Web, with the page at rest and scrolled: a slow pan, a short pan that chooses nothing, a flick, a tap on an option that began out of view), `paint` (shadows, rings, outlines, borders and corners by side and gradients against Chrome's pixels, composition across hover and focus, culling, cost), `images` (the image lab: `object-fit`, atlas regions, flips, tints, nine-slices, sizes from the picture, a picture registered or named after mounting, and an image in a scroll container, read back from the geometry and the pixels, natively and in the Web page), `transforms` (geometry through the matrix, hit testing, scrolling, focus ring, sharpness, transitions against Chrome's matrices, the squeezed-edge rows) with the negative controls of `transforms-faults`, `layout-utilities` (582 boxes against Chrome's `getBoundingClientRect` and the transitions against Chrome's curves), `text-styles` (113 texts against Chrome's boxes and lines, selection and copy, and an ink comparison), `rich-text` (every text, character and inlay of eleven pages against what Chrome reports, the geometry queries, a recolour that shapes nothing), `navigator` (every lab opened, no sideways overflow, the filter, the keys, a lab that throws), `code-editor` (the caret on its column's pixel, selection, the key table, copy and paste, IME, an edit reaching the page with its state kept, the read-only fallback) and `live-compile` (the compiler in the running realm: edits reach the pixels, a syntax error or a throwing render leaves the last good page, Bun's diagnostics at `tsc`'s offsets). `node scripts/live-compile-agreement.mjs` holds Bun's checker to `tsc` on every lab and on broken edits.

`verify:text-layout` needs a probe build of the extension (`pnpm build:native --probe`; run `pnpm build:native` afterwards to put the default back).

Options. `pnpm verify`, `verify:motion` and `verify:interaction` are `scripts/verify.mjs`: `--only=<section>[,<section>]` runs those sections of the interaction verifier, and `verify.mjs` rejects an unknown name before it builds or launches anything. The default sections are `events`, `cooperation`, `pointers`, `keyboard`, `positioning`, `inputs`, `scroll`, `selection`, `drag`, `forms`, `combobox`, `dropdown-touch`, `hidpi`, `filters`, `glass`, `paint`, `images`, `navigator`, `transforms`, `layout-utilities`, `text-styles`, `rich-text` and `code-editor` (which checks whichever path the machine has: the live editor if the live-compile extension is installed, the read-only fallback if not); `filters-sizes`, `filters-cost` (GPU cost), `filters-faults` and `transforms-faults` (negative controls) and `live-compile` (it needs the extension) run only when named; they are not counted as left out, so a plain run is not partial. `verify:interaction:web` takes `--only=` with `events`, `cooperation`, `pointers`, `keyboard`, `scroll`, `selection`, `drag`, `forms`, `combobox`, `dropdown-touch`, `hidpi`, `filters`, `glass`, `paint`, `images`, `navigator`, `transforms`, `text-styles`, `rich-text`, `code-editor` and `touch` (there is none for `positioning`, `inputs` or `layout-utilities`); an unknown name is an error there too. `--renderer=gl_compatibility|mobile|forward_plus` runs the windows on that Godot rendering method (the project's own is Compatibility; the evidence goes to a directory suffixed with the renderer). `--viewport=WxH` runs one window whose render target is that size, whatever the window's. `--faults` is only for `--only=filters-faults` and `--only=transforms-faults` and needs the library `pnpm build:native --faults` makes (a default run refuses it, and a faults run refuses a default build). `--no-retry` runs each window once. `verify:text-layout --headless` runs no pixel checks; `verify-motion-web.mjs` takes `--quick`, `--baseline` and `--acceptance`. Every script with options rejects an argument it does not take before it does any work (`scripts/arguments.mjs`); `verify:world` and `verify:a11y` take `--no-retry`. `pnpm demo` is the exception: it forwards its arguments to Godot. `--release` selects the release Web template; `--engine=stock` selects the engine profile on the verifiers, `pnpm demo`, the Web build and the typings checks (the native builds are one build and take none). The Web verifiers need Chrome (`CHROME` names its path).

For the browser target, see the [Web build instructions](WEB.md):

```sh
pnpm build:web
pnpm verify:web
pnpm verify:motion:web
pnpm verify:interaction:web
node scripts/verify-world-web.mjs   # the world-space page; it has no package script
```

The Web verifiers serve the export themselves, on a free port that only they know, and stop the server when they finish: run them with no server and no port. `pnpm demo:web` is only for looking at the export by hand (port 8096, or a free port if that is taken; `--lab=<id>` opens a lab). `GODOT_REACT_WEB_URL` names a server you started: the verifier then fetches every file of the export's receipt from it and refuses to open a browser unless each is byte for byte the export it checked (another checkout's, the other engine's, an older side module under the same pack all fail). Web uses the browser's JS runtime through GodotJS and the Rust extension compiled to a Wasm side module. It requires the matching threaded GodotJS templates and Emscripten/lazy-table ABI described in that guide, plus its separately pinned Rust nightly.

### Web hosting

**react.breaka.club.** The release Web export (`node scripts/build-web.mjs --release`) is a stripped pack: 30 files, 6.6 MiB, with no source maps and none of the verification or probe scripts (the Web verifiers use the debug export, which is unchanged). `pnpm deploy:web:plan` stages and compresses it and prints every file and what would be uploaded; `pnpm deploy:web` compresses each file once with brotli, publishes an immutable release under `react-demo/v2/` in the `breaka-asset-uploads` bucket (a manifest and content-addressed objects) and then moves a single pointer object, and deploys the Worker (`deploy/cloudflare-worker.ts`, `wrangler.react-demo.jsonc`) only when its source changed. The Worker serves the current release's page with `no-cache` and an ETag, so a deploy is picked up on the next visit and an unchanged page costs a 304; the page's `<base href="/r/<release>/">` points every relative load of the engine at one release, the large `.wasm` and `.pck` files answer there with a cacheable redirect to `/o/<hash>/<name>` so a binary that did not change between two deploys is already in the visitor's cache, and everything under `/r/` and `/o/` is `public, max-age=31536000, immutable`, sent as the stored brotli (`Content-Encoding: br`) when the browser accepts it. The bare address redirects to `/?demo=navigator`, and every response, redirects and errors included, carries `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: cross-origin`, which the threaded engine needs. A cold visit transfers about 12 MiB (it was 66.6 MiB, 52.7 MiB of it the uncompressed pack) and a returning visitor after a deploy about 2 MiB, measured in headless Chrome through the Worker on `wrangler dev` with a browser that accepts only `br`. `pnpm deploy:web:releases` lists the releases the site has shown and `pnpm deploy:web:rollback` points it back at the previous one in a single object write; `--local --persist-to=<directory>` runs a deploy against wrangler's local R2 state. `pnpm check:site --url=<address> --files` loads a site in headless Chrome, compares every file with the export's receipt, and opens the navigator, a lab and the code panel.

The Web interaction verifier sends Chrome wheel events, and Godot's Web display server makes a pixel delta of `d` into `0.03 * d` wheel ticks, so a 100 px notch is 3 ticks at device pixel ratio 1 and 1.5 at 2 (a native notch is one); a check that scrolls must expect that (`notchTicks()`). Console errors a section provokes on purpose are announced with `expectedConsoleErrors` and must appear, and the portrait navigator keeps its labs in a menu whose items exist only while it is open.

Web verification is real Chrome through Puppeteer, at device pixel ratio 1 and 2, in landscape and portrait, with a touch page, against the debug template of Breaka's engine; the `stock` profile also ran its debug and release templates. On Breaka's engine the release export ran `verify:web --release`, `verify-live-compile-web.mjs --release` and the landscape pass of the navigator section; the rest of the interaction verifier ran against the debug export. Safari, other browsers and mobile devices have not been qualified.

When Godot's Web shell (`fetchWithProgress`) finishes reading `index.pck` through `ReadableStream.getReader()`, Chromium can emit a benign `net::ERR_ABORTED` on the completed stream close after all `Content-Length` bytes are delivered; `verify-motion-web.mjs` verifies the exact byte count and SHA-256 of `index.pck` before allowing that post-completion event. The verifier also records the existing Emscripten dynamic-loader synchronization warning once before startup and treats all other runtime errors as failures.
