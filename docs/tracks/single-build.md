# Track: single build (one native build per platform, loaded by both engines)

Branch `single-build`, based on main `9dba853` and rebased onto `53d23b8` (box-mesh, the code editor on rich text and the dropdown touch fix; see "After the rebase"). Notes and report for the coordinator;
`docs/INTERACTION_PLAN.md`, `docs/INTERACTION_PROGRESS.md` and `README.md` are not edited here (the paragraph for the README is at the end). Ben decided: the native
UI library and the native live-compile extension are **one build per platform, bound to stock Godot 4.7.2's API, and loaded by both engine profiles**. This supersedes
stock-engine S2 to S4 and the whole of [engine-switch.md](engine-switch.md) for native.

Why it works: a GDExtension loads in the Godot it was bound to or a newer one, never an older one (godot-rust refuses with "compiled against newer Godot version"). A build
bound to 4.7.2 therefore loads in Breaka's 4.8, and a build bound to 4.8 cannot load in 4.7.2, which was the late failure that started the engine-switch track.
stock-engine S4 had already found no 4.8-only API in `native/**/*.rs`, and both manifests already say `compatibility_minimum = "4.7"`. Per-profile native builds, and switching
between them, had no job left. What stays per profile is the Web (a side module must be linked with the Emscripten of the engine that loads it), the GodotJS typings (GodotJS differs) and
the evidence directories.

## What it does

| Question | Answer |
| --- | --- |
| Which API are the native builds bound to? | `NATIVE_BINDING_API` in `scripts/native-binding.mjs`, the one place that names it: `version: '4.7.2'` and the dump pair `native/api/stock-4.7.2/{extension_api,gdextension_interface}.json`. `nativeBinding()` reads the dump's header and throws if it is not a dump of that version, so the record and the files cannot drift. `.cargo/config.toml` names the same two files for a plain `cargo test` or `cargo clippy`, and a test holds the two together. |
| What does a native stamp record? | `binding: { api: '4.7.2', dump: <hash of the dump pair> }`, `probe`, `features`, the library hash and the source digest. **No profile.** A Web side module's stamp still records `engine`. `stampFor` takes one of the two and throws for neither or both. |
| What does a native run check? | `engine.prepareNative` (every native launcher; `requireInstalledBuilds` again before every window of `verify`, `verify:a11y`, `verify:world`, `verify:text-layout`) checks the UI library and, if one is installed, the live-compile extension: bound to `NATIVE_BINDING_API`, the variant asked for, built from the sources as they are now. The profile does not enter into it. It also refuses an engine **older than** the binding API (a 4.7.1 binary), since that is the case that fails late in godot-rust. |
| What does a refusal tell me? | Why, and the one command: `pnpm build:native [--probe] [--faults]`, `node scripts/build-live-compile.mjs`. No `--engine=`. Both refusals come in one error. |
| Variants | `probe` and `faults` are variants of the one build: `target/`, `target/probe`, `target/faults`. None per profile. |
| Web | Per profile, unchanged: `target/web` and `target/stock-web`, Emscripten 6.0.12 (Breaka, lazy function-table ABI) and 4.0.11 (stock), `--engine=` on `build:web` and `build-live-compile-web.mjs`. The split is stated in the header and the `web` blocks of `scripts/engine.mjs`, in `docs/WEB.md` and in `native/api/README.md`. Breaka's Web side module is still bound to Breaka's own 4.8 dumps (`native/api`). |
| Typings | Per profile. `demo/typings` and `demo/gen` stay Breaka's; the stock typings are generated by the stock editor from **the one native library** (it reads `target/release`, no longer `target/stock/release`) into `target/stock-typings/typings`, and their record carries the dump hash. |

### The guard table

`tests/single-build.test.ts` runs every row through the real `engine.mjs`, `native-binding.mjs`, `live-compile-build.mjs` and `freshness.mjs` copied into a temporary repository, with a stub for `godot --version`,
under **both** profiles (the two refusals must be equal strings).

| Installed build | A native run (`prepareNative`, either profile) |
| --- | --- |
| bound to API 4.7.2, current sources, the variant asked for | goes ahead |
| bound to another API (`4.8.0`) | refused: `is bound to Godot API 4.8.0 (dump abababababab), not bound to Godot API 4.7.2 (dump c09705c3f94f). Run `pnpm build:native` first.` |
| bound to 4.7.2 by another dump (same version, regenerated) | refused, the same sentence with the two dump hashes |
| stamped by profile (every build made before this track) | refused once: `is the breaka profile's build, made before native builds were bound to one Godot API, not bound to ...` |
| stale sources | refused: names the changed files (`changed: native/lib.rs`) and the build command |
| library missing, stamp missing, or replaced after it was stamped | refused with the build command |
| a probe build for a default run, a default build for a probe run, the faults build either way | refused: `is a probe build, not a default build` / `cargo features differ` |
| live-compile extension absent | **goes ahead** (nothing loads, the code editor is read-only); the `live-compile` section is refused with the build command |
| live-compile extension present and any of the rows above, or a manifest without its library | refused with `node scripts/build-live-compile.mjs` (both lines in one error when both are wrong) |
| an engine older than 4.7.2 | refused before the builds are looked at |
| `gen:types` (`liveCompile: false`) | does not look at the extension: it takes the manifest out of the project while its editor runs |

## Decisions

**B1. Bind to the oldest API either profile runs, not to the engine under test.** The check godot-rust makes is runtime >= API, so 4.7.2 serves 4.7.2 and 4.8 and 4.8 serves only 4.8. The cost is that
Breaka's 4.8 runs a library whose class table is 4.7.2's: only the methods the library calls must exist in 4.8 with the hash it was bound with (godot-rust's `lazy-function-tables` look each up on first use). Both engines ran six
sections, including the code editor and rich text, on the one build (Evidence), but see "Not verified" for the sections that were not run.

**B2. One record, in one module, no profile.** `NATIVE_BINDING_API` names the version and the dumps; the native build, the live-compile build, the guard, the stamps and the stock typings read it. The dumps stay in
`native/api/stock-4.7.2/` (renaming files that other tracks' digests name would only churn): they are dumps of stock 4.7.2, and the *stock profile's identity* is not in any stamp. The stock profile's Web build binds to the same pair.

**B3. A stamp is bound to an engine profile (Web) or to a Godot API (native), exactly one.** `findProblem` has the two forms and keeps every Web message as it was. A native stamp that names a profile is a build from before this
track: it is refused once with a message that says so, not treated as 4.7.2-bound even when a stock build happened to be (it cannot be shown to be).

**B4. The native builds have no profile, so `--engine=` is refused there.** `pnpm build:native --engine=stock` used to mean something; silently building the same library would mislead. `build-native.mjs` and `build-live-compile.mjs` do not
call `selectEngine` and reject the flag (`rejectUnknownArguments(..., { engine: false })`) with a message that points here.

**B5. The engine must be at least the binding API.** `verifiedVersion()` already checked the profile's version prefix; it now also refuses a binary older than 4.7.2 (stock's prefix `4.7.` admits 4.7.0 and 4.7.1, which godot-rust would refuse late).

**B6. What was removed.** `pnpm switch:engine` and `scripts/switch-engine.mjs`; `assessInstall`, `installRefusal`, `installBuilt` and `switchBuild` in `freshness.mjs` and the install-from-target idea with its `installFix` and
`INSTALL_FIX`; `switchLibrary` and `switchLiveCompile`; the per-profile native target directories (`target/stock`, `target/stock-probe`, `target/stock-faults`, `live-compile/target-stock`, and `targets.native*` in the
profiles); the profile `libraryName`/`installedLibrary`; `tests/engine-switch.test.ts` and `tests/engine-switch-wiring.test.ts`. Nothing is left as a shim. A switch had one job, installing a profile's build, and there is nothing to install.

**B7. What was kept, and why.**
- `installFile` (stage a sibling, check its hash against the stamp, rename): the builds still install over a library a running Godot may have mapped.
- The early refusal of an installed live-compile extension on every native run (engine-switch E1, E2): a demo run loads the extension whether or not its section runs, so a stale or other-API extension still has to be refused up front, and an absent one is still fine.
- The stamped target directories (`target/react_ui.build.json`, `live-compile/target/live_compile.build.json`) and `prepareTarget`: they are how a build knows cargo's artifact is a build of these sources, not an install source. The live-compile build still cleans `live_compile_core` and `live_compile_ext` unless that stamp vouches for the sources, and still rebuilds `live-compile-cli` after a clean when it was there (29 tests skip without it).
- `writeGdextension` by rename, and not at all when it would not change.
- `beginBuild` in `freshness.mjs`, now the one start-a-build for the native library, live-compile and Web (it replaces three copies).
- `engine.requireBuiltLibrary`, `generateStockTypings`/`ensureStockTypings`, `apiDirectory`, `webBindingEnvironment`, `beginWebBuild`, `webSourceInputs`: the Web and the typings still need them.
- `native/api/*.json` (Breaka's 4.8 dumps): Breaka's Web build is still bound to them.

**B8. Stock typings move to `target/stock-typings`.** They lived in `target/stock/`, which was the stock profile's cargo target directory. The directory, its record and its staged project now stand alone, so removing a cargo directory cannot take them
with it, and `tsconfig.stock.json` and `.gitignore` follow. The record keys `apiSha256` became `apiDump` (the binding's dump hash), so the first `test:types --engine=stock` regenerates them once, about 10 s.

## Not verified

- **Only six native sections ran on each engine**, plus the Web `navigator` section. A library bound to 4.7.2 resolves each Godot method it calls on first use in Breaka's 4.8; a method used only by a section that did not run (events, scroll, selection, drag, forms, the filters, glass, text input) would panic there at its first call if 4.8's class table lacked its hash. `native/api/README.md` records one such case for the *stock godot-rust tables* against this custom engine (`GDScriptTextDocument::foldingRange`); with lazy tables and the 4.7.2 dump nothing of the kind appeared in these runs. The full native regression on Breaka's 4.8 is the coordinator's, and is the thing to watch.
- `--probe` and `--faults` builds were not made for real (`verify:text-layout`, `filters-faults` not run); their rows are tested in the temporary repository.
- (Closed by [stock-web.md](stock-web.md), which also found and fixed the live-compile Web side module being shared between profiles.) The stock profile's Web build and its Web verifiers were not run (the default profile's was, as asked). Its side module is stale (`.cargo/config.toml` is an input) until `pnpm build:web --engine=stock`.
- `pnpm dev`, `pnpm demo` and `gen:types` were not run for real; they call the same `prepareNative`, covered by the temporary-repository tests.
- Release builds only: the manifests name the one library for debug and release, as before.
- Breaka's Web side module remains bound to Breaka's 4.8 dumps; binding the Web builds to 4.7.2 as well was not asked and is not tried.
- **Follow-up, [stock-web.md](stock-web.md):** the table row above says the Web stays per profile, and it did for the UI library's side module, but the live-compile extension's Web side module was still one shared file, built only for Breaka. A stock export therefore shipped Breaka's module and the stock page died at load. It is per profile now, stamped with its profile, and an export holds exactly its own or none.

## Merge notes

What every checkout must build once, after merging, before its next demo run (a run says so, with the command, and refuses before any window opens):
1. `pnpm build:native` (the installed stamp names a profile, or none, so it is refused once; cargo recompiles godot-rust against the 4.7.2 dumps: about 3 min cold, much less when the target directory has built that binding before).
2. `node scripts/build-live-compile.mjs` where the extension is installed (same reason; 2 min).
3. `pnpm build:web` per profile in use, and `node scripts/build-live-compile-web.mjs` where the Web live-compile module is used: `.cargo/config.toml` changed, and it is an input of every build's digest.
4. The stock typings regenerate by themselves on the next `test:types --engine=stock` (about 10 s) into `target/stock-typings`.

Safe to delete afterwards, to get the disk back: `target/stock`, `target/stock-probe`, `target/stock-faults` (if present) and `live-compile/target-stock`. Nothing reads them. The main checkout's installs are not touched by this branch; the coordinator rebuilds there after landing.

Anything that wrote `pnpm build:native --engine=...` in a note or a script now fails with a message that says why (the other tracks' notes keep the commands as they were run then).

## README text

The native UI library and the native live-compile extension are one build per platform. They are bound to the Godot 4.7.2 API (`NATIVE_BINDING_API`, `scripts/native-binding.mjs`; the dumps are `native/api/stock-4.7.2`), which Breaka's 4.8 loads as well as the
stock 4.7.2 does: a GDExtension loads in the Godot it was bound to or a newer one. So `pnpm build:native` and `node scripts/build-live-compile.mjs` build once, install over the one path the `.gdextension` names, and record the API and the dump hash they were bound to (not a
profile); `--engine=` does not apply to them and is refused. Every native run refuses a library or extension bound to another API, built from older sources, or the wrong variant (`--probe`, `--faults`), before any window opens, and says which command to run. Switching
`--engine=stock` and the default needs no build or install. What remains per engine profile is the Web (`pnpm build:web --engine=<name>`: a side module is linked with the Emscripten of the engine that loads it, 6.0.12 for Breaka's, 4.0.11 for stock), the
GodotJS typings (`demo/typings` are Breaka's; the stock ones are generated by the stock editor into `target/stock-typings`) and the evidence directories. Details and decisions: [docs/tracks/single-build.md](docs/tracks/single-build.md).
