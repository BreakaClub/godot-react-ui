Branch `utilities-text` (merged to main as `19910f2`, merge `5956068`) built the utilities; branch `text-finish` added this file, the
`text-styles` verifier section and the fixes the section found. Tailwind 3.4.17 is the reference for the classes, and headless Chrome
156 on macOS for how they render. Decision log entries are numbered T1 to T15 for the coordinator to fold into `docs/INTERACTION_PLAN.md`.

## Decisions

**T1. Faces are registered per root, by a `#[func]`.** `ReactUiRoot.registerFontFace(family, weightMin, weightMax, italic, font)` (typed
by `registerFontFace(root, {family, weight, style, font})` in `src/fonts.ts`). A static face has one weight; a variable font gives the
range of its `wght` axis. Per root, like a Godot `Theme`, so the HUD and a world panel can differ and nothing is process-global. Text
that names no registered family keeps the theme font, so a tree with none of this costs nothing and the library works with the theme
font alone. A newly registered face shapes again the text that names a family (`refresh_font_users`).

**T2. Matching is CSS Fonts 4 step 4, and the browser's synthesis follows it.** Style first (an italic request takes the italic faces if
any), then weight: an exact cover wins; 400 to 500 look up to 500, then lighter, then heavier; below 400 lighter first; above 500
heavier first (`face.rs`, ten unit tests). A variable face draws the requested weight on its axis (`FontVariation.variation_opentype`,
keyed by the axis' tag as an integer: the string `"wght"` is not accepted, `"weight"` is) and clamps outside its range, as Chrome does
(Open Sans here covers 300 to 800, so `font-thin` and `font-light` are the same face, and `font-black` is 800). Bold is made up when the
request is 600 or more and the face is lighter than 600 (`FontVariation` embolden by Skia's amount: size/24 at 9 px down to size/32 at
36 px), italic when the request is italic and the face is not (a skew of 0.25, Skia's). The theme font is one face of the weight and
style it declares; Godot's default is Open Sans SemiBold, static, 600, so `font-bold` on it changes nothing (a browser would do the same)
and `italic` slants it. Chrome and the library agree on every weight, style and family of the lab to within the widths below.

**T3. Line height: half-leading, with whole-pixel space above and below and a fractional gap between lines.** CSS puts half of what the
glyphs leave over above them and half below, the first line included; Blink floors the upper half to a pixel (`CalculateLeadingSpace`).
The text server has integer extra space above and below each line (`SPACING_TOP`, `SPACING_BOTTOM`, set on the paragraph's shaped text so
they do not multiply `FontVariation`s) and a float `line_spacing` between lines. `LineBox::of` splits a line height into the two
whole pixels and the fraction, and the fraction is added to the paragraph's height once more, since the server leaves out the gap after
the last line. A unitless value (`leading-relaxed`, `text-5xl`'s `1`) stays a factor and each element multiplies it by its own size; a
length (and `em`, `%`) becomes px where it is set (`settle`). Tailwind's size classes carry their paired line height, so `text-sm` is now
20 px tall per line where it was the font's 23: every layout with text changes (T14). An element with no line height keeps the font's own
ascent and descent. Godot's ascent is FreeType's, rounded up (Open Sans 16 px: 18, 5); Chrome rounds hhea (17, 5), so a baseline can be a pixel
lower than Chrome's (below).

**T4. Letter spacing: the text server's own fractional advance.** The integer spacings (`FontVariation.set_spacing`,
`TextServer.font_set_spacing`, `shaped_text_set_spacing`, glyph spacing) cannot give `tracking-tight` at 14 px, which is -0.35 px, and
rounding it is out. Evaluated, with the numbers measured on Breaka 4.8 and stock 4.7.2 (identical):

1. *Shape at a larger size with integer spacing and draw under a scale.* Works for layout, but the glyph cache is keyed by oversampling
   with `CLAMP(level, 0.1, 100) * 64` (`font_draw_glyph`, `text_server_adv.cpp:4272`), so a transform of 1/s with the oversampling divided by s
   is clamped at s = 10 at ratio 1; and every glyph shaped at the large size is rasterised at the large size (`_ensure_glyph`), 40 KB at 280 px, 180 KB
   at 640 px, per glyph. Measured: `fixed_size` on a duplicated `FontFile` keeps the cache at the real size and scales the advances exactly
   (width at 14 x 20 divided by 20 = the width at 14), so it can be made to work, at the price of every consumer of the shaped text (carets,
   selection, accessibility text runs the engine reads itself) being in the scaled unit.
2. *Draw the glyphs yourself from `shaped_text_get_glyphs`.* Needed anyway (below), but it leaves the wrapping to the server, which does not know the spacing.
3. **Chosen: the text server adds `embolden * size / 64` px to the advance of every glyph it shapes** (`_get_extra_advance`, `text_server_adv.cpp:3508`;
   a double, the last glyph of the text included, as CSS adds letter-spacing; zero-width glyphs excluded). So a `FontVariation` with
   `embolden = spacing * 64 / size` shapes the text with exactly that spacing: measured 0.2273 px/glyph for embolden 1.0 at 14 px (the
   formula's 0.21875 plus the server's rounding of the whole line up), negative values narrow. Everything the server then reports
   (wrapping, widths, carets, selection runs, hit tests, accessibility) is the real geometry, in real pixels, with no conversion anywhere.
   The cost is that the shaping font's outlines are emboldened, which nothing may see, so a tracked paragraph is drawn glyph by glyph
   (`draw_glyphs` repeats `TextServer::shaped_text_draw`) with each glyph's font swapped for the same font without the embolden. It relies on an
   engine behaviour that its documentation does not state; `native/fonts.rs` tests the formula, and the verifier's tracking pages (twelve steps, every
   named one at two sizes, odd sizes) fail if it stops being true. Optional ligatures are turned off for a tracked text (`liga`, `clig`), as CSS does.

**T5. A tracked, decorated, fractionally spaced or centred paragraph is drawn line by line.** `StyledParagraph::draw` takes
`TextParagraph::draw` when nothing needs more. Otherwise it builds the text layout (`GodotParagraph`, which replicates the paragraph's own
line placement), draws each line's baseline on a device pixel (a browser snaps it; at ratio 2 a gap of 0.75 px would otherwise blur a line), clips as `TextParagraph::draw` does,
draws underline and overline before the glyphs and the line through the text after.

**T6. Case: the shown text is the source text transformed, and it is what is shaped, selected and copied.** Chrome copies the transformed text
(`getSelection().toString()` on `text-transform: uppercase` gives `STRASSE, DON'T STOP...`; `scripts/text-styles-golden.json`, `case-upper`), so the selection
document counts the shown text (`Visual::shown`, `selection_text_of`); the source is the `text` prop, which accessibility names. Offsets JS sees count the
shown text. `uppercase` and `lowercase` are Unicode full case mapping (`ß` is `SS`, final sigma). `capitalize` follows Chrome's output
(read off 28 separators, `probe4`): a letter after anything that is not a letter, digit, underscore, apostrophe or middle dot starts a word, so `e.g.` is `E.G.` and `hello-world` is
`Hello-World`, though Unicode's word boundaries would keep both whole.

**T7. White space.** Unset behaves as `pre-wrap` (React Native's `Text`: newlines break, spaces are kept), so no existing text changes; `whitespace-normal`, `nowrap`
and `pre-line` collapse as CSS does (`flow.rs`), `pre` and `pre-wrap` do not, and tabs advance to multiples of eight spaces. `break-normal` (long words overflow), `break-words` (a
word wider than the line is broken: `BREAK_ADAPTIVE`) and `break-all` are the three; the default is `break-normal`, where the code before this track broke long words
(an old default that was also why a flex item could shrink to one letter).

**T8. Min-content is `f32::MIN_POSITIVE`, not `0`.** `TextServer::shaped_text_get_line_breaks` wraps only when `width > 0`:
`servers/text/text_server.cpp:1086` (the Breaka checkout; `shaped_text_get_line_breaks_adv` has the same test at 903) is `if ((l_width > 0) && (width + adv > l_width) && (last_safe_break >= 0))`, so width `0.0` means *no wrapping* and
the min-content width of a text measured at `0.0` was its max-content width. The smallest positive width breaks at every opportunity, and
`last_safe_break >= 0` is false until the first word ends, so the first word is never broken and the widest word is the minimum. Under `break-words` the
adaptive flag is taken off for this measurement only, because `overflow-wrap: break-word` does not make a word's break points count for min-content (`anywhere` does).

**T9. Decoration geometry is Blink's, read off its pixels.** `underline` is `max(1, floor(size/10))` px thick (`from-font`: the font's thickness, at least 1) and starts
`max(1, ceil(size/20))` px below the baseline (an explicit `underline-offset` replaces that gap, an explicit thickness is used as given); `line-through` is centred a third of the ascent above the baseline;
`overline` ends at the ascent. All are worked out in CSS px and each edge is rounded to a device pixel, so a line is never blurred (`metrics.rs`, tests with the
rows measured in Chrome at 12 to 48 px and ratios 1 and 2). Chrome draws underlines with `text-decoration-skip-ink: auto`, which breaks the line round descenders; the library draws
it whole, and the reference page sets `skip-ink: none`. Propagation follows CSS Text Decoration 3: a decoration set on an element draws in its colour and thickness on the
text below it, the in-flow descendants only (an `absolute` or `fixed` one is not decorated), and `no-underline` below cannot remove it.

**T10. Overflow.** `truncate` and `text-ellipsis` ellipsise a line (`OVERRUN_TRIM_ELLIPSIS`) only when the element clips (`overflow` not `visible`), as CSS does. `line-clamp-N`
is `max_lines_visible`, whose last line the server ends with an ellipsis; `text_layout.rs` now lays out a paragraph that hides lines as the lines it shows.

**T11. Justification and alignment.** `text-justify` is `HORIZONTAL_ALIGNMENT_FILL` with word-bound justification, the last line left alone and the space a line ends with trimmed
(`JUSTIFICATION_TRIM_EDGE_SPACES`: without it every justified line stopped one space short of the edge, found by the verifier). `text_layout.rs` supports `FILL`
(a justified line is as wide as the box, and starts at its left, or at its right when it runs right to left).
`text-start` and `text-end` are left and right: there is no `direction`.

**T12. The space a line ends with hangs.** In CSS the space at the end of a wrapped line does not count in the line's width, so right aligned and centred text ends and is centred on its glyphs.
`TextParagraph::draw` aligns by `shaped_text_get_width`, which counts the space and is rounded up to a whole pixel. The text layout of a `Text` now measures a line by the sum of its
glyphs' advances without the space it ends with (`GodotParagraph::hanging_spaces`; a text input keeps the server's width), and centred and right aligned text is drawn where that layout puts
it (T5). Found by the verifier: `text-end` was 3.6 px short of Chrome's right edge.

**T13. `antialiased` compiles to no style, and the reason is measured here.** Chrome on macOS draws glyphs about 12 % heavier than the same glyphs with
`-webkit-font-smoothing: antialiased` (the section "Is our text lighter than Chrome's?" below). The library draws the lighter one. So `antialiased` is what it already does, and
Chrome without it is the heavier look that the library does not imitate. `subpixel-antialiased` is not accepted: it would promise LCD coverage that is not drawn.

**T14. Pinned layouts.** Tailwind's pairs change the height of every text that uses a size class, and the default for long words changed (T7); the tests that pinned a class as
unsupported or a font size alone (`tests/styles.test.ts`, the commit fixture) now expect `{ fontSize, lineHeight }`.

**T15. At a fractional ratio every baseline is snapped to a device pixel.** The `hidpi` section failed at content scale 1.5 with the merged utilities: "React text ends on a pixel row as a Godot Label's does at content scale 1.5: vertical step
0.502 against 1.000". Its text is `text-2xl` (24 px, now with Tailwind's line height of 32), whose first baseline is at 33 logical px, which is row 49.5 at 1.5 (`GODOT_REACT_HIDPI_MEASURE` "stems baseline": logical 33, device 49.4999986; at ratio 2 it is 66),
so the glyphs' ends were split across two rows. A baseline is the half-leading plus the ascent, both whole logical pixels, and an odd one is a half row at 1.5; the paired line height of `text-2xl` is the likely change from before the merge (the section was not run on main itself; the failing run is `artifacts/logs/verify-interaction-full-1.log`, the baseline measure `verify-hidpi-1.log`). `TextParagraph::draw` puts baselines on whole *logical* pixels, so it is exact only when
the oversampling is a whole number; `StyledParagraph::draw` now takes the line by line path (which rounds each baseline to a device pixel, T5) whenever the oversampling is not a whole number. Ratios 1 and 2 keep `TextParagraph::draw`.

## Is our text lighter than Chrome's?

Ben's question: on macOS, Godot's text looks lighter and thinner than Chrome's while the shapes match; is it DPI scaling? Answer: **it is Chrome's font smoothing. DPI scaling
accounts for about 2 % of the ink, in Chrome as much as in ours, and nothing remains.**

Method. The 113 texts of the lab (13 pages, `demo/src/text-styles-data.ts`) are rendered three ways at each ratio: headless Chrome 156 with its default smoothing, the same page with
`-webkit-font-smoothing: antialiased` (`scripts/text-styles-reference.mjs --smoothing=antialiased`), and the library's own render from the native `text-styles` section's captures
(Breaka 4.8, `artifacts/native-interaction/landscape/text-styles-<page>-dpr{1,2}.png`, the default window: ratio 1.0 is 560 x 400 logical, ratio 2.0 is the same logical size at 1120 x 800 pixels).
For each text's cell (its box and two pixels around it) the script sums the ink, `(255 - luma) / 255` over the pixels, divided by the ratio squared so the unit is ink per logical pixel squared, and
adds the cells (`node --import tsx scripts/text-styles-reference.mjs --diff --native=<captures>`; the pictures with the three renderings and the difference are in `artifacts/utilities-text-compare/<page>-dpr{1,2}.png`,
the numbers in `report.json`).

| | ratio 1.0 | ratio 2.0 |
| --- | --- | --- |
| ink, Chrome default | 96759 | 96717 |
| ink, Chrome `antialiased` | 85834 | 83930 |
| ink, ours | 85994 | 84378 |
| Chrome default over `antialiased` | **1.127** | **1.152** |
| ours over `antialiased` | **1.002** | **1.005** |
| ours over Chrome default | 0.889 | 0.872 |
| 95th percentile of the pixels' darkness (Chrome, aa, ours) | 255, 250, 251 | 255, 255, 255 |

- **Smoothing: all of it.** Chrome's default smoothing puts down 12.7 % (ratio 1) and 15.2 % (ratio 2) more ink than the same glyphs with `antialiased`, and our text is 11 % and 13 % lighter than Chrome's
  default for that reason: ours is within 0.2 % and 0.5 % of the `antialiased` ink. Page by page ours over `antialiased` is between 0.985 and 1.017 at ratio 1 and between 0.963 and 1.036 at ratio 2 (the low end is the
  `whitespace` page: Chrome lets `break-normal`'s long word overflow its 100 px cell into the next cell and the library clips it at the box, a limit below; the high end is `numerals`, a six text page); `weights-sans` at ratio 1 is 8068 against 8068. Against `antialiased` the mean per pixel difference is 4.04 levels where against Chrome's default it
  is 5.08, and the share of pixels more than 24 levels apart is 4.3 % against 5.6 %; at ratio 2 the two are 8.31 and 8.61.
- **DPI: about 2 %, the same in Chrome.** From ratio 1 to ratio 2 our ink falls 1.9 % (85994 to 84378) and Chrome's `antialiased` ink 2.2 % (85834 to 83930); Chrome's default smoothing does not change
  (96759 to 96717). Whatever causes that 2 % (not investigated) it happens to both renderers. A glyph rasterised at the wrong scale would be far off, as a quarter of the ink or more, at one ratio only;
  neither ratio is. D45's oversampling is doing its work (the viewport's own oversampling is passed to every text draw).
- **What remains: nothing measurable.** The pixel peaks agree (250 and 251 at ratio 1, saturated at 2). The comparison is of the library's render buffer, not of the screen, so the display's own gamma is outside it.
- **Control.** `--diff` fails (exit 1) when our ink is more than 3 % from Chrome's `antialiased`, and also fails when Chrome's default smoothing is *inside* that band, so the check can tell the two looks apart: today the first
  is 0.2 % and 0.5 % out, the second 12.7 % and 15.2 %.

So `antialiased` is correctly a no-op (T13): it is the look the library has. A page that wants Chrome's heavier default for a reference comparison simply leaves the class off *in the reference*, which is what
`scripts/text-styles-reference.mjs` does for the `chrome-*` renders, and the `chrome-aa-*` renders add the class. If the heavier look is wanted in the library it is a separate feature (thickening the glyphs); nothing was built, as nobody has asked for it.

## Verification

The `text-styles` section (`demo/src/verify-text-styles.ts` natively, `scripts/verify-text-styles-web.mjs` on the Web; `node scripts/verify.mjs --interaction --only=text-styles`, `--engine=stock` for stock 4.7.2, and
`node scripts/verify-interaction-web.mjs --only=text-styles`) holds the lab to what headless Chrome 156 reports for the same class strings (`scripts/text-styles-golden.json`, written by
`node --import tsx scripts/text-styles-reference.mjs --golden`, which also asserts that Chrome's layout is the same at ratios 1 and 2).

- **Numbers.** For each of the 113 texts: box x, y, width and height, and for each line its baseline, left edge (not for a line that starts with a space) and right edge, all within 1 logical pixel of Chrome's. `truncate`, `ellipsis`,
  `clip` and `tracking-wrap-edge` are held to the box only (Chrome keeps every character's rectangle past an ellipsis; the last is the wrapping limit below) and `line-clamp-N` to the lines it shows.
  `GODOT_REACT_TEXT_STYLES_SPREAD` logs each page's mean and worst difference: right edges within 0.17 px everywhere but `tracking-center` (0.92, the whole-pixel centring below), baselines equal to Chrome's or one pixel off, heights within 0.75 px.
- **Selection and copy** for the eight texts that matter (bold, `tracking-widest` and `tracking-normal` at 16 px, a tracked wrapping text, `leading-relaxed`, uppercase, capitalize, italic serif): a drag from one of Chrome's character rectangles to another, every
  seventh character, selects exactly the characters between; the painted highlight (the blue tint in the raster) spans the characters Chrome puts there to a pixel; a triple click and the copy chord put on the clipboard what `copy` gives in Chrome
  (the transformed text, T6). The caret is not here: a `Text` has none, and `TextInput` is not styled.
- **Controls** (each fails when it should): a text held to the numbers of its neighbour (one step of leading, of tracking, of weight, of size; seven pairs) must be found wrong, and a drag placed by the characters of `tracking-normal-base` must *not* select
  what the `tracking-widest-base` drag does.
- **Ratios.** Natively at ratio 1 and, in the landscape window (1120 x 800 device pixels), also at 2; portrait at 1 (`--viewport=` sizes give a logical-size image, so the default windows are used). The Web scenario runs the four windows
  (landscape and portrait, each at ratio 1 and at the retina ratio 2).
- **Pictures.** Each page is captured (`text-styles-<page>-dpr{1,2}.png`); `node --import tsx scripts/text-styles-reference.mjs --diff --native=<captures>` writes the four-up pictures (Chrome, Chrome `antialiased`, ours, the difference times four) to
  `artifacts/utilities-text-compare/<page>-dpr{1,2}.png` and `report.json`, and fails on the ink bands above.

## What `tests/utilities-text.test.ts` covers

## Limits that stay

- **`TextInput` is not styled.** It still shapes with the theme font (`text_input_godot/shaping.rs::shape`): weight, family, tracking, line height and the other utilities are
  accepted on it and do nothing. Its caret, selection, undo and IME code is unchanged by this track (the `forms` section covers it). The `Text` node is the whole of what was built.
- **A word that ends within a space width of the line's end wraps one word early.** `TextServer::shaped_text_get_line_breaks` tests `width + advance > line width` at the space after
  the word, so the space cannot hang as it does in CSS (`tracking-wrap-edge`: "over" ends 0.5 px inside a 220 px line and the library wraps before it; Chrome keeps it). It is a
  break in about one line of sixty. Right aligned and centred lines do hang their spaces (T12).
- **A baseline can be a pixel lower than Chrome's.** FreeType rounds the ascent up (Open Sans 16 px: 18), Chrome rounds hhea (17). Where the half-leading then floors differently the baseline is one pixel
  apart; no baseline is further than that in the lab (below). Reading hhea from the font bytes would remove it and was not done.
- **A centred line sits on a whole pixel.** `TextParagraph::draw` places it at `floor((box - line) / 2)`, and the text layout replicates that so that carets and hit tests agree with the drawing (`text_layout.rs`, `TextAlignment::Center`).
  Chrome centres on the fraction, so a centred line can be up to a pixel from Chrome's: `tracking-center` ends 0.92 px short of Chrome's (the largest right-edge difference of the 113 texts, in the `GODOT_REACT_TEXT_STYLES_WIDE` log; Chrome puts the line at 86.891, a whole pixel is 86). The floor loses less than a pixel, so it stays inside the verifier's tolerance by construction; it was not changed.
- **Underlines are whole.** Chrome breaks them round descenders (`text-decoration-skip-ink: auto`); the library does not. `decoration-solid|double|dotted|dashed|wavy` classes are not accepted.
- **Glyphs from a fallback font are not tracked** (the extra advance is the shaping font's) and their ascent can make a line taller; with a line height set, CSS ignores fallback metrics.
- **Offsets JS sees count the shown text** when a transform or white space changes its length.
- **Text wider than its box is cut at the box** (`TextParagraph::draw` clips each line to the paragraph's width; the line-by-line draw does the same, to match), where CSS lets it overflow; an unbreakable word in
  wrapping text is not ellipsised.
- **`break-keep` is accepted and does nothing** (`word-break: keep-all` parses, and `wrapping_of` only reads `break-all`); `font-synthesis` and `text-wrap: balance|pretty` (`text-balance`) are not accepted.
- **The default font's advances.** A `FontFile` with the default `subpixel_positioning` (`Auto`) rounds advances above 20 px to whole pixels; the lab sets one quarter on its fonts (`demo-fonts.ts`), which is the font owner's choice.
- **Cost.** Centred or right aligned text that wraps, tracked text, and decorated text build a text layout each time they are recorded (a few server calls per line and a read of each line's glyphs); a left aligned
  plain text still costs one `TextParagraph::draw`. Faces and `FontVariation`s are cached by request and never freed (bounded by the distinct styles in use).
- **Web.** The text path is the same code compiled to wasm; the section above passes there in all four windows. The Web run does not measure ink (the `--diff` comparison is native), and nothing here was tried at a fractional ratio on the Web.
- **`cargo fmt --check` fails on main** in `native/motion.rs`, `scroll.rs`, `style_engine.rs` and `text_input_godot/keys.rs` (other tracks' lines); every file of this track is clean.

## README text

Text utilities. `font-thin` to `font-black`, `italic`, `font-sans|serif|mono` and `font-['Name']` choose a face from the families registered with `registerFontFace(root, { family, weight, style, font })`
(CSS font matching: the nearest weight, an italic face when the family has one, a slant or a thickening made up when it does not; a variable font's `wght` axis draws any weight in its range). Text that names no
registered family keeps the theme font. `text-sm` and the other sizes carry Tailwind's line heights; `leading-*`, `tracking-*` (fractions of a pixel are exact), `uppercase|lowercase|capitalize`,
`underline|overline|line-through` with `decoration-*` and `underline-offset-*`, `truncate`, `text-ellipsis`, `line-clamp-1` to `6`, `whitespace-*`, `break-normal|words|all`, `text-justify` and the numeral classes
compile to longhands and render as Chrome renders them, to within a pixel (`docs/tracks/utilities-text.md` has the numbers and what differs). Unset `white-space` behaves as `pre-wrap`, as React Native's `Text` does.
