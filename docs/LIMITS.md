# Current limits

What is not built, on purpose or not yet, and what is built but has not been shown to work the way a user would meet it. Anything not listed here is built. Details: [native/PROTOCOL.md](../native/PROTOCOL.md), [WORLD_SPACE.md](WORLD_SPACE.md).

**Not built, on purpose.**

- A JSI-style binding that bypasses GodotJS's method marshalling (revisit only if measurements show the GDExtension call boundary is the bottleneck).
- A Godot `Control` per element, including `LineEdit` and `TextEdit`; a custom engine module (a proven Web engine bug is fixed in the engine's `platform/web`, not by an export-time patch).
- Drag and drop with other Godot `Control`s (`_can_drop_data` is synchronous on `&self`, where a JS answer cannot be had; `endedOutsideRoot` plus the release point is what a game uses).
- Raw text outside `<Text>`, `contenteditable`. (Rich, nested text runs are built: "Rich text".)
- CSS stacking contexts: `zIndex` orders the siblings of one paint parent, as in React Native.
- Touch text-selection handles, long-press menus, native context menus, spellcheck.
- Animated programmatic scrolling, overscroll bounce, `position: sticky`, rounded clip masks (clipping is rectangular; border radius changes paint, not the clip), native list virtualization. (2D transforms are built; 3D is recorded below.)
- Pen-specific pointer data: a pen is reported as a mouse.

**Not built, recorded.**

- *Styles.* There is no DOM, full CSS cascade, selector engine or Tailwind plugin support; this is a strict subset and the compiler throws on what it does not know. Still rejected: `space-*`, `divide-*`, `float-*`, `clear-*`, `columns-*`, `inline`, `inline-*`, `table*`, `contents`, `list-item`, `sticky`, `isolate`, `collapse`, `min-w-min` and the other intrinsic keywords on a minimum or maximum size, `max-w-prose`, `calc()` in a size, `grid-cols-subgrid` and `content-baseline` (each throws with a message that names what to use); `animate-*` and general `@keyframes` animations or animation callbacks; images (`bg-size`, `bg-position`, `bg-repeat`, `object-*`, `url()` and radial or conic gradients) and custom materials; dashed, dotted and double `border-*` and `outline-*`; logical sides (`border-s`, `rounded-ss`) and the `*-opacity-*` classes (use an opacity modifier on the colour); `text-wrap` and `text-balance`, `hyphens-*`, `indent-*`, `align-*` (vertical alignment), `font-synthesis` and `subpixel-antialiased`; `perspective` and `preserve-3d`; and the variants `dark:`, `group-*:`, `peer-*:`, `first:`, `odd:`, `before:`, `print:`, `motion-reduce:`, `max-*:`, `aria-*:` and `data-*:`. `break-keep` is accepted and does nothing. Grid has tracks and a line or span per item, not template areas or subgrid. Both overflow axes clip together (`hidden`, `scroll` or `auto` on either clips the padding box). Mixed pixel and percentage transitions, and intrinsic transitions on a flex main axis whose `flexGrow` and `flexShrink` are not zero, are rejected when the commit is validated if a `transition` names the property; under `transition-all` they jump quietly, and a style change native itself causes (a hover, a breakpoint) that would need one is applied without animation and logs an `ERROR`. `transition-all` animates the properties native can (sizes, opacity, colours, filters, transform, box shadow): padding, margin, gap, insets and radii jump.
- *Layout utilities.* `w-min` on a wrapping flex container gets the narrowest width but one line of height (Taffy); `flex-1` in a column of unknown height shares the container's height by the boxes' own heights where Chrome takes the content; a flex-shrunk box with an `aspect-ratio` keeps the height of its unshrunk width; `order` changes layout, not paint or hit-test order; there is no inline layout, float or table layout, and viewport units resolve against the root's size.
- *Text styles.* The utilities do nothing on a `TextInput`, which shapes with the theme font. A word that ends within a space width of the line's end wraps one word early (about one line in sixty). A baseline can be a pixel lower than Chrome's (FreeType rounds the ascent up where Chrome rounds hhea), and a centred line sits on a whole pixel, up to a pixel from Chrome's. Underlines are whole where Chrome breaks them round descenders. Glyphs from a fallback font are not tracked and can make a line taller. Text wider than its box is cut at the box where CSS lets it overflow, and an unbreakable word in wrapping text is not ellipsised. Offsets JS sees count the shown text when a transform or white space changes its length.
- *Rich text.* A span takes colour, background, family, weight, style and decoration only (no size, letter spacing, case or numerals), an inlay holds plain text, and a nested `Text` has no ref, handler, `role`, `testID`, state class or breakpoint class. Caret positions are by line box: a mixed-direction line has two carets at a direction change and `getCaretRect` answers the primary one; bidirectional text and a span that splits a grapheme cluster were not compared with Chrome. `auto` thickness on dotted and dashed lines, dash positions between device pixels and the round dots of a 4 px dotted line differ from Chrome's. The demo's fonts have no CJK glyphs, so such characters take their room and draw nothing in a span.
- *Shadows, borders and gradients.* Borders, radii and outline widths are whole logical pixels in paint (layout takes the float). A gradient is laid out over the padding box and drawn under the border; beyond it, it holds its end colours where CSS tiles the image, which shows only under a translucent border. The corner arcs of a plain rounded box (one `StyleBoxFlat` call) sit 0.3 to 0.5 pixel inside Chrome's at 45 degrees. The first draw of a shadow bakes its mask on the CPU (1.7 ms for `shadow-2xl` at device pixel ratio 1, 6.5 ms at 2; a transition of `box-shadow` bakes the masks of each frame, which was not measured in the engine).
- *Transforms.* `perspective`, `transform-style: preserve-3d` and `backface-visibility` are not built. A feasibility experiment (nothing under `native/` changed) showed that a transformed element with its subtree rendered into its own render target and drawn as one canvas item with a homography shader matches Chrome (interior mean difference 0.01 to 0.13 levels of 255 for perspective, 0.9 to 1.6 for `preserve-3d` cubes and intersecting planes, 1.1 to 1.3 for nested surfaces, on both engines and all three renderers); the Rust implementation is estimated at about 4,000 lines and six weeks, and the Web (WebGL2) was not run. An `overflow` clip in a frame that a transform rotates or skews is drawn as the box round the rotated rectangle, with one `ERROR` per element (hit testing is exact); translate, scale, mirror and quarter-turn clips are exact, and an exact rotated clip needs a render target per clipped element. Scrollable overflow ignores transforms, `touch-action` axes are screen axes, `zIndex` makes no stacking context for a transform either, a `relative` element between a transform and a `fixed` descendant is that descendant's containing block here and in CSS it is not, and the blur radius of a `filter` is not scaled by a transform on it. A border whose sides differ in colour, an outline and a shadow ring (baked masks) and the focus ring (a `StyleBoxFlat` stroke) keep one feather length, so under a squeeze their edges are not antialiased per axis. While a transform transition runs, a box and its text keep the drawing they had and are drawn again when it settles (a cost proportional to the subtree). What is left of the difference from Chrome on `rotateX` and `rotateY` at device pixel ratio 2 is Chrome's own resampling of a squeezed layer.
- *Scrolling.* Scrollbar track clicks (paging), pull to refresh, snap points. A wheel or pan gesture chains from one container to the next event by event, with no latching.
- *Select.* Radix's press-drag-release, item groups and separators, `position="item-aligned"`; moving the pointer over an item cut by the list's edge focuses it and scrolls it into view (`focus()` has no `preventScroll`). A prevented press is never a pan, so a kit part that prevents a press to manage focus loses touch scrolling unless it exempts touch, as the `Select` and `Combobox` lists do; a finger that begins a swipe on a `Combobox`'s clear or trigger button or on a chip's remove button (they prevent the press so as not to take focus from the input) cannot pan the page.
- *Combobox.* No virtualisation and no `items` prop: a thousand options cost what a thousand `Select` items cost, and a keystroke over that many re-renders them all. The platform accessibility tree for it was read once on the `stock` profile and no expectation was written from the reading, and the live region of `Combobox.Empty` is not in the lab.
- *Text selection.* Word-granularity dragging after a double click (in a `TextInput` it exists), caret affinity at wraps and direction changes, highlighting a selected line break, auto-scroll while selecting.
- *TextInput.* Native IME has not been checked by hand with a macOS Japanese or Pinyin input source (the Web IME was driven through Chrome's CDP). Engine behaviour that stays: the engine's IME start drops the last queued raw key; after a Web composition ended by a focus move `ime_started` stays set and raw keys are dropped until one more composition commits (an engine bug, to be fixed in the engine); the Right presses of two keys in one frame add up, so a text typed in a hurry into the middle of a field leaves the native caret too far right, and the caret after JS puts an edit back mid-text is off until the next key. A click inside a composing input cancels the composition without committing it. `clipboard_get` on Web returns what the previous call read, so anything else that calls it is still stale (the root's own paste no longer does). The IME window and the on-screen keyboard are placed from the root's own screen transform, which is wrong for a root on a quad in a `SubViewport`. `multiline` cannot change after creation. A triple click selects all of a text area's text, not a line.
- *Drag and drop.* Files and `setDragImage`. The ghost of a filtered source is unfiltered, and it does not follow a change of display scale mid-drag.
- *Accessibility.* `aria-labelledby`, `aria-describedby`, `aria-haspopup`, `aria-pressed` and `aria-invalid` are not typed or sent (`aria-activedescendant` and `aria-controls` are); tooltip text and its action; list and tree item counts and positions; a numeric step; `aria-live` is sent but untested. Each scroll re-sets every exposed descendant while a screen reader is attached, instead of moving one content element as `ItemList` does. The engine cannot convey a group or radio-group element, a mixed checkbox, a text area's value, a read-only field, or a scroll view's position and actions to the macOS adapter (recorded as `GODOT_REACT_A11Y_GAP`; scroll bar elements carry the position).
- *Display scale.* `CanvasItem.oversampling_with_scale` (a root whose own `scale` is above 1 draws at the viewport's level). Glyph caches at levels no viewport owns are not freed: about 20 MiB after drawing at levels 1, 2 and 3 (in use there are two sets, bounded, freed with the font). Layout and borders round to whole logical pixels.
- *World space.* No occlusion test, one quad per owner, back faces take no input, pan and magnify gestures, joypad and `ui_*` focus navigation are not forwarded, the cursor shape is not applied, hover is not re-tested when the quad or camera moves without the mouse, and the anchored label is not clamped to the window.
- *Engine behaviours not worked around.* A trackpad pan gesture reaches Godot's `Input` twice, so JS gets two `wheel` events for one pan (and Godot's own `ScrollContainer` scrolls twice); Godot's Web display server maps a DOM `deltaX > 0` to `WHEEL_LEFT`, so horizontal wheel ticks have the opposite sign on Web; on Web a touch's `pointerId` is the browser's contact identifier, which keeps counting across taps, not `2 + index`; GodotJS's V8 has no `Intl`, so libraries that need it need a polyfill natively.
- *Platforms.* The release addon carries macOS x86_64, Linux x86_64 and Windows x86_64 libraries, built by CI and never run; only Apple Silicon macOS has been run natively. A local `pnpm build:native` builds the host's library only. The live-compile extension and the quiet verifier windows are macOS only.
- *Builds.* The freshness guard does not cover the Rust and Emscripten toolchains beyond `rust-toolchain.toml`, the engine, the compiled JavaScript or the tracked `demo/typings`. The native builds are bound to Godot 4.7.2 and an older engine is refused; Breaka's 4.8 resolves the methods the library calls on first use, so a method missing from its class table would fail at its first call.
- *The code editor and live compile (demo only).* Completions are not built; hover is the name and the type (no documentation text, types printed with qualified names) and inlay hints are parameter names and the inferred types of variable declarations (no inferred return types, callback parameter types or object property names). A render that throws loses the state of the tree that threw (React discards it): the last good version renders again from its first render, and the class check only covers a mistyped literal `className`. Only the files of the lab's project can be edited, the project is the labs' TSX plus the declarations of the library, React and the ES2022 lib files (a lab that imports anything else gets TS2307), `import.meta` and top-level `await` are diagnostics, and leaving a lab drops its edits. Moving up and down keeps the column in code units, so over a line with wide characters the caret lands by code unit, not by x. The extension needs a Bun checkout for its vendor step and its own Rust nightly, and its Web side module is built for the `breaka` profile only and adds about 2.3 MiB (brotli) to a cold visit though nothing uses it until the code panel opens (loading it on first use was designed, not built).
- *The lab navigator.* It is not shown in a window narrower than about 300 logical pixels, and most labs were written for 560 and wider; a window or scene lab is not shown inside it; the error panel shows the stack with its absolute file paths; the Filters explorer offers eight of the verifier's fixtures; the Events lab's danger buttons blank the window for 600 ms before the navigator returns on the same lab with its state reset.
- *Web hosting.* The bucket is never pruned (old releases stay so open tabs keep working); a cold visit pays one extra round trip for the redirects of the large binaries and the bare address's redirect is `no-store`; the page's progress bar counts the pack and the engine module, not the side modules; `main.js` still carries the verifiers and CodeMirror (sharing and trimming them would save about 0.36 MiB of a 12.2 MiB first visit); Cloudflare Web Analytics injects its beacon (a zone setting).

**Not verified** (built, but not shown to work in the way a user would meet it).

- Native IME and VoiceOver by hand; platform focus (the verifier's window is not the key window, so the accessibility run skips it); the actions on a text field through a real adapter (the dump tool performs none).
- The platform accessibility tree on Breaka's engine, which has no accessibility driver: `pnpm verify:a11y` runs the Godot-side half there and ends "not verified" (exit 2). The macOS tree was read on the `stock` profile only. Windows (UI Automation) and Linux (AT-SPI) trees were not read, a reversed scroll axis and `scrollbar-width: none` were not read in the real tree, and the Web engine has no accessibility code.
- The kit controls and positioning have no Web verifier section of their own (the Web interaction verifier has none for `inputs` or `positioning`), so touch on the kit `Slider` was not exercised by a verifier (the lists of `Select` and `Combobox` are, in `dropdown-touch` and `combobox`). The world-space anchored label is verified natively only. IME and on-screen keyboards through a `SubViewport`, and a `SubViewport` that updates only when visible, were not exercised.
- Filters: a render target with a transparent background (a `SubViewport` with `transparent_bg`) under a frosted panel; the GPU cost on Forward+, and the cost on Web; the engine's truncation of a group's negative region, whose fix is unit-tested but did not reproduce on a real renderer.
- Whether headless Chrome reaches the system pasteboard, and the engine's own last step onto the Mac's pasteboard, because measuring writes to it (verifier runs never touch it).
- Safari, Firefox and real mobile devices. The Web touch pages (forms, combobox, dropdown lists, the code editor) are headless Chrome with emulated touch and the engine's hidden input element, so what a phone's soft keyboard does when focus moves inside a touch (iOS Safari may close and not reopen it), its autocorrection and Android's composing text were not seen; the release Web export on Breaka's engine ran only what [DEVELOPMENT.md](DEVELOPMENT.md) lists.
- The single native build on Breaka's engine: a library bound to 4.7.2 resolves each Godot method on first use in 4.8, and only the navigator, live-compile, code-editor, rich-text, transforms and paint sections ran on both engines with it; the full interaction suite on Breaka's engine is the check for the rest. Builds with `--probe` and `--faults` were not made for the single-build track, the stock profile's Web build and Web verifiers were not run with it, and `pnpm dev` and `gen:types` were exercised only through the shared refusal code.
- Rich text: the stock engine's Web export; a real high-density display (the Web's ratio 2 is puppeteer's emulated scale); right-to-left text; the platform accessibility tree of a text with spans (the accessible name was read from the snapshot).
- The code editor and live compile: a real IME and a real soft keyboard (the composition events are synthesised), native at device pixel ratio 2 (the Web retina page covers the grid, the caret and the waves at that scale), the machine's real clipboard on the desktop (the section uses the root's in-process one), Safari, Firefox and iPad, and a line with CJK glyphs (none is registered in the demo, so the geometry is verified and the glyphs are not on screen).
- The stock engine's release export was not built.
- Transforms: IME placement under a transform; Combobox: what native costs for a long list (the 1,000-option numbers are JavaScript and the commit's size only).
- No native or Web negative controls were run for the `forms` section (five unit mutants of the `TextInput` fixes were killed), and the Web scenario that makes the soft-keyboard race deterministic is not timing-proof on a real tablet.
- The cost of hit testing (a paint-tree descent per mouse move) and of rebuilding the selection document for each gesture was not measured at scale; both are linear in the tree.
- Not done in the verifiers: an assertion count for `verify`, `verify:motion`, `verify:world` and `verify:a11y`, which are one linear script each with no section that could be left empty (the interaction and Web verifiers fail a section that made no assertion).
